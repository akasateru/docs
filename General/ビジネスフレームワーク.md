# ビジネスフレームワーク

エンジニアが事業・プロダクト側と共通言語で議論するために知っておくと良いビジネスフレームワーク群。市場規模の考え方（TAM・SAM・SOM）を起点に、関連する戦略・優先順位づけ・指標系のフレームワークを整理する。

## 1. TAM・SAM・SOM（市場規模の3階層）

市場規模を段階的に絞り込んで捉えるフレームワーク。事業計画・投資家向け資料で頻出。

- **TAM (Total Addressable Market)**：総市場規模。そのプロダクトが理論上到達しうる最大の市場全体。業界レポートやマクロ統計から算出することが多い。
- **SAM (Serviceable Available Market)**：実際にアプローチ可能な市場規模。TAMのうち自社のビジネスモデル・提供地域・ターゲット顧客に合致する部分。
- **SOM (Serviceable Obtainable Market)**：実際に獲得可能な市場規模。SAMのうち競合状況・自社リソースを踏まえて現実的に取れる部分。短中期の売上予測に直結する。

3つは入れ子構造（TAM ⊃ SAM ⊃ SOM）になっている。

### 1.1. 算出方法

- **トップダウン方式**：業界統計・調査会社レポートから市場全体を出し、割合を掛けて絞り込む
- **ボトムアップ方式**：「顧客単価 × 想定顧客数」を積み上げて算出する。根拠が明確で投資家に説得力を持たせやすい

### 1.2. 注意点

- TAMを大きく見せすぎない。投資家は「本当にSAM/SOMまで現実的に落とし込めているか」を見る
- 算出根拠（出典・仮定条件）を明示する
- 市場環境・自社の実行力の変化に応じてSOMは定期的に見直す

## 2. TAM・SAM・SOMに関連するフレームワーク

- **STP分析** (Segmentation, Targeting, Positioning)：市場を切り分け(Segmentation)→狙う層を選び(Targeting)→自社の立ち位置を決める(Positioning)。SAM/SOMを決める前段の思考プロセスとして併用される。
- **ビーチヘッド戦略**（Geoffrey Moore『Crossing the Chasm』）：SOMの中でもさらに最初に攻める「一点突破」の市場を選ぶ考え方。スタートアップの初期戦略でよく使われる。
- **Technology Adoption Lifecycle**：顧客をイノベーター→アーリーアダプター→アーリーマジョリティ…と分類。SOMを「どの層から獲得するか」で捉える視点。
- **SOW (Share of Wallet)**：個々の顧客が特定カテゴリに使う予算のうち自社が獲得できる割合。B2Bでよく使う。

## 3. エンジニアに有用なその他のビジネスフレームワーク

### 3.1. 優先順位づけ系（プロダクト開発で直接使う）

- **RICE** (Reach, Impact, Confidence, Effort)：機能開発の優先度をスコアで比較。開発工数(Effort)が分母に入るのでエンジニアの見積もりが直接効いてくる。
- **ICE** (Impact, Confidence, Ease)：RICEの簡易版。
- **Kano Model**：機能を「当たり前品質」「魅力品質」「一元品質」に分類し、どこに工数を割くべきか判断する。
- **WSJF** (Weighted Shortest Job First)：SAFeで使われる、コスト・オブ・ディレイ(遅延コスト)÷開発期間でバックログを並べる手法。技術的負債の優先度議論にも応用しやすい。

### 3.2. 指標・グロース系

- **AARRR (Pirate Metrics)**：Acquisition→Activation→Retention→Referral→Revenueの5段階でファネルを見る。どこで離脱しているかをログ設計・分析の観点から追いやすい。
- **North Star Metric**：事業全体の健全性を表す単一指標。KPI設計で「何をダッシュボードの中心に置くか」の指針になる。
- **LTV / CAC**：顧客生涯価値と獲得コスト。インフラ・サーバーコストの意思決定（この機能にどこまでコストをかけていいか）にも関わる。

### 3.3. 戦略・意思決定系

- **Jobs to be Done (JTBD)**：「顧客はこの製品を“雇って”何を成し遂げたいか」という視点。要件定義やUX設計で「なぜこの機能が必要か」を掘り下げるのに有効。
- **Lean Canvas / Business Model Canvas**：1枚で事業全体（課題・解決策・収益モデルなど）を可視化。新機能や新規プロダクトの企画書代わりに使える。
- **Build-Measure-Learn**（Lean Startup）：仮説検証サイクル。MVP開発やA/Bテスト設計の思考フレームとして馴染みやすい。
- **SWOT分析**：強み・弱み・機会・脅威の整理。技術選定や自社プロダクトのポジショニング議論で使える。

### 3.4. 実務接続度が高い順（エンジニア視点）

1. **RICE/ICE** — バックログ優先度づけで日常的に使える
2. **JTBD** — 「なぜこの仕様か」を経営・PM側と共通言語で議論できる
3. **AARRR/North Star** — 自分の書いたコードが事業指標にどうつながるか説明できるようになる
4. **Cost of Delay/WSJF** — 技術的負債の解消を「先送りコスト」として定量的に主張できる
