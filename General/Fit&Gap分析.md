# Fit&Gap分析

システム導入・パッケージ選定の際に、「あるべき姿（業務要件）」と「候補システムが持つ機能」を突き合わせ、一致点（Fit）と不一致点（Gap）を洗い出す手法。ERPパッケージやSaaS選定などで用いられる。

## 1. 基本の考え方

上流工程全体における位置づけは以下の通り。Fit&Gapは「候補選定〜要件定義」の間に位置し、単独では成立しない。

```text
As-Is分析 → 要求定義(RFP) → 候補選定 → Fit&Gap分析 → To-Be設計 → 要件定義 → 設計・開発
```

| 区分 | 意味 |
| --- | --- |
| **Fit（適合）** | 業務要件をシステムがそのまま満たせる部分 |
| **Gap（乖離）** | システムが要件を満たせない・満たすが不十分な部分 |

Gapが見つかった場合の対応方針は主に3つ。

1. **アドオン開発**：システム側をカスタマイズして要件に合わせる
2. **業務側を変更（BPR）**：業務プロセスをシステムの標準機能に合わせる
3. **運用回避**：手作業や代替手段でカバーし、システム改修はしない

## 2. 進め方

1. 業務要件を洗い出し、一覧化する（要求一覧）
2. 候補システムの標準機能を要件ごとに突き合わせる
3. 各項目を「Fit」「Gap」「一部Fit」などで判定する
4. Gap項目について対応方針（上記3つ）と工数・コストを検討する
5. 結果を関係者に提示し、導入可否や追加開発の判断材料にする

## 3. 関連概念

| 概念 | 内容 |
| --- | --- |
| **As-Is / To-Be** | 現状業務（As-Is）とあるべき業務（To-Be）。GapはAs-IsとTo-Be、あるいはTo-Isと標準機能の差として捉える |
| **RFP（提案依頼書）** | 発注側がベンダーに要件を提示する文書。Fit&Gapの元になる要件一覧はここから派生することが多い |
| **Fit to Standard** | 業務をシステムの標準機能に合わせる導入方針。近年のSaaS/クラウドERP導入（S/4HANA Cloud等）で主流。「アドオンを増やさない」思想 |
| **BPR（業務プロセス再設計）** | Gapを埋める手段の一つ。システムでなく業務を変える発想 |
| **MoSCoW優先順位付け** | Must/Should/Could/Won't。Gap項目に優先度をつけて対応要否を判断する際に使う |
| **フィット率** | 全要件のうちFitした割合。パッケージ選定の定量指標としてよく使われる（例：「フィット率85%」） |
| **アドオン/カスタマイズ vs コンフィグレーション** | Gap対応が「設定変更（コンフィグ）」で済むか「プログラム改修（アドオン）」が必要かの区別はコスト・保守性に直結する |
| **CEMLI / RICEFW** | SAP・Oracle文化圏で使われる、アドオンの分類フレームワーク（Conversion, Extension, Modification, Localization, Integration 等）。Gap対応の型を体系化したもの |

## 4. 実務上の注意点

- **Gapの「見せ方」が意思決定を左右する**：同じGapでも「業務側で回避可能」と書くか「必須改修」と書くかで結論が変わるため、判定基準（誰がどう判定するか）を最初に決めておく
- **Gapが多い＝悪ではない**：Fit率だけで判断せず、Gapの重要度（コア業務への影響か周辺業務か）で評価する
- **コスト積算とセットで見る**：Fit&Gap表だけでなく、Gap対応ごとの概算工数・費用を並べて初めて意思決定材料になる
- **将来の保守性への影響**：アドオンを増やすとバージョンアップ時の改修コストが積み上がる（いわゆる「塩漬け」問題）。Fit&Gap段階でこの論点を説明しておくべき

## 5. 関連ドキュメント体系

Fit&Gap分析の成果物は単体でなく、以下と連動して管理されるのが一般的。

- 要件一覧（要求仕様書）
- Fit&Gap一覧表（要件×判定×対応方針×工数）
- 業務フロー図（As-Is/To-Be）
- 概算見積り・導入計画書
