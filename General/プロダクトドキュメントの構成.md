## 1. ディレクトリ構成

情報整理においてディレクトリ構成は重要
必要な情報を見つけやすいのに加え、情報の整理に役立つ

```bash
my-product-docs/
├── 01_Concepts/            # 【概念】プロダクトを「点」で理解する
│   ├── business-logic/     # 業界知識、計算ロジック、制約事項
│   └── data-models/        # ER図、エンティティの定義
├── 02_Solutions/           # 【ガイド】プロダクトを「線」で理解する
│   ├── use-cases/          # 「注文する」「退会する」などの主要ユースケース
│   └── user-flows/         # 画面をまたぐ一連の動作（既存の機能・画面を繋ぐ）
├── 03_Reference/           # 【リファレンス】プロダクトを「詳細」に記録する
│   ├── screens/            # 画面仕様（コンフルの「画面」に対応）
│   └── features/           # 機能仕様（コンフルの「機能」に対応）
└── 04_Resources/　         # リンク、画像、議事録など
```

## 2. 長い文章の構成フレームワーク

「まとめ→詳細」という構造は、複数のドキュメント設計フレームワークで標準化されている方法論。

- **Executive Summaryパターン**: 最初に1ページ程度のサマリーを置き、その後に詳細章を続ける。ビジネス文書やレポートの定番。多忙な人は概要だけ読んで、必要に応じて詳細に潜れる
- **Inverted Pyramid（逆ピラミッド）**: ジャーナリズム由来。最も重要な情報（まとめ）を最初に、次に補足、最後に詳細という構造。読者が途中で止めてもある程度理解できる
- **Topic Sentence + Detailsパターン**: 各章の冒頭に「この章で何を扱うか」を1〜2文で書き、その後に詳細を展開。見出しだけ読んでも全体構造が分かる
- **Outline-Driven Structure**: トップダウンで設計。最初に全体の目次・アウトラインを提示し、各項目を掘り下げていく（§1のディレクトリ構成もこの発想）

### 2.1. 実践的なポイント

- **階層の深さを制限する**: 3段階くらいが限界。深すぎるとナビゲーションが煩雑になる
- **各見出しは自己完結的に**: 見出しと最初の段落を読めば、その章の役割が分かるようにする
- **冗長を避ける**: 概要と詳細で同じ内容を繰り返さない。詳細では「その理由」「具体例」「背景」を足す
- **リンク・目次活用**: 長文なら目次から各章にジャンプできる仕掛けがあると便利

### 2.2. 文書の種類で変わる型

- **内部ドキュメント**（設計書、運用マニュアル）→ 目次 + アウトライン + 詳細
- **対外資料**（提案書、レポート）→ Executive Summary + 詳細が無難
- **技術仕様書**→ Quick Start + Referenceという二層構造も多い

### 2.3. プロダクト内部仕様書の標準構成

```text
1. 概要（1-2ページ）
   - プロダクトの目的、ターゲットユーザー、解決する問題

2. 要件一覧（サマリー）
   - 機能要件、非機能要件、制約条件

3. 詳細仕様（メイン部分）
   （各機能ごとに: 目的、ユースケース、入出力、エラーハンドリング等）

4. データモデル・API仕様
   （スキーマ、エンドポイント、レスポンス形式）

5. システムアーキテクチャ（図解含む）

6. 実装上の注意点
   （パフォーマンス、セキュリティ、テスト戦略等）
```

見出しの粒度は「5分で読める量」を目安にし、機能ごとに同じ構成（目的→入力→処理→出力→エラー）をテンプレート化して繰り返すと、読み手が予測可能な構造で読める。

## 3. 機能理解の6軸フレームワーク

検索機能の中の「ファジー検索」「アイテム軸検索」、絞り込み機能の中の「価格フィルター」「セクションフィルター」のように、プロダクトの機能を細かく切り分けたあと、各機能を体系的に理解するための共通フレームワーク。どの機能でも以下の6軸で整理すると、プロダクト全体が同じ形式で見えるようになる。

1. **目的・コンテキスト**: 何のための機能か。誰が、どんな状況で使うか
2. **入力・パラメータ**: 何を受け取るか。どの形式か。制約はあるか
3. **処理・アルゴリズム**: 内部でどう動くか。どんなロジックで判定・計算するか
4. **出力・結果**: 何を返すか。どの順序でソートされるか。メタデータは含まれるか
5. **パフォーマンス・スケール**: 処理時間、対応規模、キャパシティ制限、リアルタイム性
6. **制限・エッジケース**: 使えない場合、異常系の処理、フォールバック動作

### 3.1. 適用例（セクションフィルター）

- **目的**: カテゴリ階層をナビゲートして、ユーザーが興味のあるアイテムに絞り込む
- **入力**: カテゴリツリー上の1つ以上のノード選択
- **処理**: 選択されたカテゴリ配下の全アイテムを取得、他フィルターと組み合わせてAND/ORで絞り込み
- **出力**: マッチしたアイテムリスト、パンくずナビゲーション表示
- **パフォーマンス**: カテゴリキャッシュ、200ms以内の応答
- **制限**: 最大10階層、同時選択は5カテゴリまで

「ファジー検索」と「セクションフィルター」は別の機能でも、同じ6軸で理解できるので、チーム内で「この機能の場合は◯◯が必要」という判断が揃いやすくなる。

### 3.2. DDD文脈での応用: 層ごとの整理

DDD（Domain-Driven Design）で設計している場合は、機能を6軸ではなく**層ごと**に整理する方法も有効。実装を意識した整理になる。

典型的なDDD層構造（User Interface/Presentation・Application・Domain・Infrastructure の4層）に沿って、たとえば「セクションフィルター」を説明すると:

```text
【セクションフィルター】

ドメイン層
- 概念: カテゴリによる商品の分類・階層構造
- ドメイン知識: 「カテゴリは最大10階層」というビジネスルール

アプリケーション層
- ユースケース: 「ユーザーがカテゴリを選択して結果を表示する」
- 流れ: 入力 → ドメインロジック適用 → 結果返却

インフラ層
- 実装: カテゴリツリーのキャッシング方法
- 技術選択: どうDBから取得するか

UI層
- ユーザーが見る: カテゴリツリー、チェックボックス、結果数
```

チームの会議についていくための「パッと検索してパッと確認できるまとめ」を作る場合も、6軸または層構造のどちらかをテンプレートとして機能ごとに埋めておくと、後から高速に参照できる。
