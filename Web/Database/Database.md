### 4.1. ハッシュインデックスとポインタの類似点

- **ハッシュインデックス**: キーをハッシュ関数にかけ、そのハッシュ値から直接データの格納位置（バケット）を求める仕組み。
- **ポインタ**との類似点: どちらも「値」から「実体の位置（アドレス）」への参照を得るという点で概念的に近い。
  - ポインタ: メモリアドレスを直接指す1対1の参照。
  - ハッシュインデックス: ハッシュ関数を経由した間接参照であり、複数のキーが同じハッシュ値になる**衝突（コリジョン）**が起こり得るため、チェイン法やオープンアドレス法などの衝突解決が必要になる点がポインタと異なる。
- **B-treeとの使い分け**: ハッシュインデックスは等価検索（`=`）が高速だが、範囲検索（`<`, `>`, `BETWEEN`）や順序を使ったソートには向かない（ハッシュ値に順序性がないため）。範囲検索が必要な場面はB-treeが使われる理由の一つ。

## 8. グラフ型データモデル

データを**ノード（頂点）**と**エッジ（辺）**の集合として表現するデータモデル。リレーショナルモデル（テーブル）やドキュメントモデルと並ぶ代表的なデータモデルの一つ。

- **ノード**: エンティティ（人、物、イベントなど）
- **エッジ**: ノード間の関係。方向性・ラベル・重みを持てる
- **プロパティグラフ**: ノードにもエッジにも属性（key-value）を持たせられるモデル（Neo4j, Amazon Neptuneなど）
- **RDFモデル**: 主語-述語-目的語のトリプルで表現するモデル（セマンティックウェブ、知識グラフで使用）

**得意なこと**: 「友達の友達」のような多段の関係をたどるクエリ、経路探索、推薦。リレーショナルDBだと大量のJOINが必要になる処理を、グラフでは隣接関係を辿るだけで高速に処理できる。

**代表用途**: SNSの人間関係、知識グラフ、不正検知（取引ネットワーク）、レコメンデーションシステム

### 8.1. ヘテロジニアスグラフ（Heterogeneous Graph）

**複数の種類のノード・エッジを持つグラフ**のこと。「ヘテロジニアス」＝「異種の」という意味の一般的な形容詞で、グラフ以外の文脈（例: CPU+GPUを組み合わせるヘテロジニアスコンピューティング）でも使われる。

- **ホモジニアスグラフ**（対義語）: ノードもエッジも1種類のみ（例: SNSの「ユーザー-フォロー-ユーザー」だけのグラフ）
- **ヘテロジニアスグラフ**: 複数タイプが混在する（例: 学術グラフの「著者」「論文」「会議」「トピック」といった複数ノードタイプと、「執筆する」「引用する」「所属する」といった複数エッジタイプ）

知識グラフはほぼ例外なくヘテロジニアスグラフである。近年ではグラフニューラルネットワーク（GNN）の分野でも、ノードタイプごとに異なる重み行列を使う **Heterogeneous GNN**（HAN, R-GCNなど）が発展している。

「ヘテロジニアスなグラフ型データモデル」＝複数種類のエンティティ・関係を持つグラフDB設計、という文脈で語られることが多い（知識グラフ構築、レコメンデーションシステムなど）。

## 9. Apache Cassandra

大量データを複数のコモディティサーバーに分散して扱うために設計された、無料でオープンソースの分散型NoSQLデータベース。もともとFacebookが開発し、後にApacheプロジェクトへ寄贈された。§6の「NoSQL採用例（Twitter）」で触れたCassandraの詳細。

### 9.1. 主な特徴

- **分散型アーキテクチャ**: マスターレス（単一障害点がない）なノード構成。複数のデータセンターにまたがるクラスタを非同期レプリケーションでサポート
- **CAP定理上の位置づけ**: 「一貫性」より「可用性」と「スケーラビリティ」を優先する設計。書き込みスループットが非常に高い用途に強い
- **ワイドカラム型データモデル**: 柔軟なスキーマで、疎（スパース）な列を大量に持つデータも効率的に扱える
- **線形スケーラビリティ**: ノードを追加するだけで読み書きスループットが線形に伸び、サービスを止めずに拡張可能
- **耐障害性**: データを複数ノードに複製するため、ハードウェア障害があってもデータが失われにくい

### 9.2. 現状のログ（2026-07-12時点）

- 最新の安定版は **Cassandra 5.0.8**（2026年4月リリース）。サポート対象バージョン系列は3つ
- 5.0系列の主要新機能:
  - **Storage-Attached Indexes (SAI)**: 効率的なセカンダリインデックス
  - **Vectorデータ型・検索**: SAI経由の近似最近傍探索（ベクトル検索対応、AI関連ワークロード向け）
  - **Unified Compaction Strategy (UCS)**: 適応型コンパクション
  - **Trie Memtables / Trie SSTables**: トライ構造ベースのメモリ/ディスク格納形式
  - **Dynamic Data Masking**: クエリ時に機密データを選択的にマスキング
- 5.0.8では6.0から**自動リペア機能（CEP-37）**をバックポート、`cassandra-stress`でのTLS 1.3自動ネゴシエーション対応なども追加

## 10. キーの種類

リレーショナルDBにおける「キー」には、役割に応じて複数の種類がある。

- **主キー（Primary Key）**: テーブル内の各行を一意に識別するキー。NULL不可・重複不可。
- **候補キー（Candidate Key）**: 一意性の条件を満たし、主キーになり得るキーの候補。1テーブルに複数存在してよく、その中から1つが主キーに選ばれる。
- **複合キー（Composite Key）**: 複数のカラムを組み合わせて一意性を持たせるキー（単独のカラムでは一意にならない場合に使う）。
- **外部キー（Foreign Key）**: 他テーブルの主キー（または候補キー）を参照し、テーブル間の関係（リレーション）を表すキー。参照整合性を保証する。
- **代理キー（Surrogate Key）**: 連番やUUIDなど、業務的な意味を持たない人工的な主キー。
- **自然キー（Natural Key）**: メールアドレスやマイナンバーなど、業務データ自体が持つ意味のある値を主キーとして使う場合のキー。
- **ユニークキー（Unique Key）**: 一意性制約を持つが、主キーではないキー（NULLは許容される場合が多い）。

主キー・外部キーには通常インデックスが張られる（外部キーは自動では張られないDBもあるため要確認）。§4のカーディナリティ・インデックスの話とあわせて、「一意性を保証する制約」と「検索を高速化する仕組み」は別軸の概念であることに注意。

## 11. データバックフィル（Data Backfill）

**データバックフィル**とは、過去に遡ってデータを補完・再生成する処理のこと。通常の日次バッチなどが「今日分だけ処理する」のに対し、バックフィルは「過去の特定期間をまとめて再処理する」という点が特徴。

### 11.1. 主なユースケース

- **新しい集計ロジックを過去データにも適用したい**: 例）先月から新しい売上集計カラムを追加したが、それ以前のデータにも同じ計算を適用したい
- **パイプラインの不具合によるデータ欠損の復旧**: 例）バッチ処理が数日間失敗しており、その期間のデータが抜けている
- **新しいテーブル・データウェアハウスの構築**: 過去のログや取引データを新しいスキーマに合わせて流し込む

### 11.2. 実行時の注意点

- **冪等性**: 同じ期間を何度実行しても結果が変わらないようにする（再実行・リトライに耐える設計にする）
- **負荷**: 大量の過去データを一気に処理するとDB・ジョブに負荷がかかるため、期間を分割する等の配慮が必要
- **整合性**: 既存データを上書きするのか追記するのかを事前に明確にする

## 12. NewSQL

**NewSQL**とは、「RDBMSライクなSQL・ACIDトランザクション」と「NoSQL並みの水平スケーラビリティ」を両立させることを狙った分散データベースのカテゴリ。代表例はGoogle Cloud Spanner。

### 12.1. Spannerのコスト構造

- **ノード / PU（Processing Unit）単位の課金**: サーバーレスではなく、最小構成でも常時起動コストが発生する（PUはノードをより細かく分割した課金単位）
- **マルチリージョン構成にすると複製コストが跳ね上がる**
- 小〜中規模ワークロードでは Cloud SQL や AlloyDB の方が圧倒的に安く、Spannerは過剰投資になりやすい

### 12.2. NewSQLが本当に必要になる条件

RDBMS（+ リードレプリカ、キャッシュ、必要なら手動シャーディング）で足りるケースが大多数であり、NewSQLが効いてくるのは以下が**同時に**成立する場合に限られる。

1. **書き込みが単一プライマリで捌ききれない**（読み取りはレプリカでスケールできるが、書き込みは1台がボトルネックになり垂直スケールにも上限がある）
2. **複数リージョンにまたがり、かつ強整合性（ACID / external consistency）を落とせない**（例: グローバル在庫管理、金融決済）

この2条件が揃わない限り、RDBMSで「非同期レプリケーションで整合性を諦める」か「手動シャーディングで複雑さを抱える」方が運用コスト・金銭コストともに安く済むことが多い。「将来スケールしそうだから」という理由だけで先回りしてNewSQLを選ぶのは典型的な過剰設計であり、まずPostgresで作り、書き込みが実際にボトルネックになってから移行を検討するのが安全。

### 12.3. OSSのNewSQL選択肢

| 製品 | ライセンス | 特徴 |
| --- | --- | --- |
| CockroachDB | コアはOSS（BSL/Apache混在、要確認） | Spannerに近い設計思想。PostgreSQL互換 |
| TiDB（PingCAP） | Apache 2.0 | MySQL互換。HTAP対応でOLAP寄りの用途にも強い |
| YugabyteDB | Apache 2.0 | PostgreSQL互換 |
| Vitess | Apache 2.0 | MySQL自体をシャーディングする方式。YouTube/Slack実績あり。「NewSQL」というよりMySQLスケーリング層 |

自前運用の手間を許容できるなら、PostgreSQL互換で情報も多いCockroachDBかYugabyteDBが試しやすい。

### 12.4. 「ノード」の一般的な意味

分散システムにおける**ノード**とは、データを保存・処理する計算単位（サーバー/プロセス）のこと。DB全体を1台ではなく複数のノードに分割し、各ノードがデータの一部（シャード）を担当してCPU/メモリ/ディスクI/Oを分担する。ノードを増やす（スケールアウト）ことで全体の処理能力・容量を線形に近い形で拡張できる。Kafkaのブローカー、Elasticsearchのシャード担当ホスト、Kubernetesのワーカーマシンなども同じ意味で「ノード」と呼ばれる（§8のグラフの「ノード（頂点）」とは別概念）。

## 13. レプリケーションとシャーディング

DBをスケールさせるための2つの基本技術。解決する問題が異なるため、実際の大規模システムでは両方を組み合わせて使うことが多い。

### 13.1. レプリケーション（Replication）

**同じデータを複数のサーバーにコピーして持つ**こと。データ量そのものは減らせないが、可用性と読み取り性能を上げられる。

- **Master-Slave（Primary-Replica）**: 書き込みはMasterのみ、読み取りはSlaveにも分散できる。最も一般的な方式
- **Master-Master**: 複数ノードが書き込み可能。競合解決が必要で複雑
- **同期レプリケーション**: Slaveへの反映完了を待ってから書き込み完了を返す。整合性は高いが遅い
- **非同期レプリケーション**: Master側で書き込み完了後すぐ返す。速いが一時的にデータがずれる（レプリケーションラグ）

弱点: 書き込み性能はMaster1台の限界を超えられない（Master-Slave方式の場合）。

### 13.2. シャーディング（Sharding）

**データを複数のサーバーに分割して分散配置**すること（水平分割）。書き込み性能の向上とデータ量の分散が目的。

- **レンジベース**: IDや名前の範囲で分割（A-M, N-Zなど）。範囲検索に強いが偏りやすい
- **ハッシュベース**: キーをハッシュ化して分散。均等に分散しやすいが範囲検索が苦手
- **ディレクトリベース**: どのシャードにあるかを管理テーブルで管理。柔軟だが単一障害点になりうる

弱点: クロスシャードのJOINやトランザクションが困難。リシャーディング（再分割）のコストが高い。

### 13.3. 併用パターン

各シャードごとにレプリケーションを組む構成が一般的（例: MongoDBのSharded Cluster、§9のCassandraはリング構造にレプリケーションとシャーディングを統合済み）。

```text
[Shard 1: A-M]  [Shard 2: N-Z]
   ├─Master        ├─Master
   ├─Slave         ├─Slave
   └─Slave         └─Slave
```

「データ量の分散（シャーディング）」と「可用性・読み取り性能（レプリケーション）」を両立させる狙い。

## 14. MongoDB

**ドキュメント指向DB**（JSON風のBSON形式）。§9のCassandraと対照的に、明確なMaster（Primary）を置く設計。

### 14.1. レプリケーション: Replica Set

```text
        [Primary]  ← 書き込みはここだけ
         /      \
   [Secondary] [Secondary]  ← 読み取り可能、Primary障害時に自動昇格
```

- **Primary**が唯一書き込み可能。Secondaryは非同期でデータを複製
- Primary障害時は投票により新Primaryへ**自動フェイルオーバー**
- 読み取りをSecondaryに逃がすことも可能（ただしレプリケーションラグに注意）

### 14.2. シャーディング: Sharded Cluster

```text
[mongos router]
      |
  ┌───┴───┬───────┐
[Shard1] [Shard2] [Shard3]   ← 各ShardはそれぞれReplica Set
```

- **shard key**を指定してデータを分散（レンジベース／ハッシュベースを選択可）
- `mongos`ルーターがクエリを適切なshardへ振り分ける
- `config server`がどのデータがどのshardにあるかのメタデータを管理
- shard keyの選び方が重要。偏ると特定shardだけ肥大化する「ホットスポット」問題が起きる

### 14.3. Cassandraとの対比

| | MongoDB | Cassandra（§9） |
| --- | --- | --- |
| データモデル | ドキュメント（JSON/BSON） | ワイドカラム |
| Master | あり（Primary） | なし（全ノード対等・マスターレス） |
| シャーディング | 明示的に設定（shard key） | リング構造（コンシステントハッシュ）に組み込み済み |
| 一貫性 | 強整合性寄り（CP寄り） | 調整可能。デフォルトはAP寄り（Tunable Consistency: ONE/QUORUM/ALLなど） |
| 得意なこと | 柔軟なスキーマ、複雑なクエリ | 超大量書き込み、単一障害点のない高可用性 |

MongoDBは「レプリケーション」と「シャーディング」を別レイヤーの機能として組み合わせる設計、Cassandraは最初から一体化した設計、という対比が理解の軸になる。

## 15. SQLコマンド分類（DDL / DML / DCL / TCL）

SQL文は「何を対象にするか」で4種類に分類される。名前が似ていて覚えにくいが、**対象が「入れ物」→「中身」→「権限」→「一連の操作」の順に大きくなっていく**と捉えると区別しやすい。

| 分類 | 正式名称 | 対象 | 代表コマンド | ロールバック |
| --- | --- | --- | --- | --- |
| **DDL** | Data **D**efinition Language | 器（構造） | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` | 不可（自動コミット） |
| **DML** | Data **M**anipulation Language | 中身（データ） | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | 可（COMMITまで） |
| **DCL** | Data **C**ontrol Language | 権限 | `GRANT`, `REVOKE` | DB依存 |
| **TCL** | Transaction **C**ontrol Language | 一連の操作 | `COMMIT`, `ROLLBACK`, `SAVEPOINT` | ―（ロールバックそのもの） |

### 15.1. 覚え方

- **D**efinition＝定義＝テーブルという「箱」を作る/壊す
- **M**anipulation＝操作＝箱の「中身」を出し入れする
- **C**ontrol（DCL）＝「誰が触れるか」を制御する
- **C**ontrol（TCL）＝「一連の操作をまとめて確定/取り消す」を制御する
- 使う順番も大体この通り：まずテーブルを`CREATE`（DDL）→データを`INSERT`/`UPDATE`（DML）→必要なら権限を`GRANT`（DCL）→複数の変更をまとめて`COMMIT`（TCL）

### 15.2. 分類名がDCLとTCLで両方「C」なのがややこしい点の整理

- DCLの C = 誰が(Who)アクセスできるかの制御（**認可**の話）
- TCLの C = 一連の変更を確定するか取り消すか の制御（**まとまりの単位**の話）
- 対象が全く違う（DCL＝ユーザー権限、TCL＝変更の確定タイミング）と意識すれば混同しにくい

### 15.3. TRUNCATEがDMLではなくDDLである理由

`TRUNCATE`は見た目上「データを消す」のでDML（`DELETE`）と混同しやすいが、実際はテーブルという「器」を作り直す操作（内部的に一度DROPして再CREATEに近い）のためDDLに分類される。そのため`DELETE`と違い、行ごとの条件指定（`WHERE`）ができず、多くのDBで自動コミットされ`ROLLBACK`できない。
