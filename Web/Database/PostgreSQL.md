## 1. 概要

- PostgreSQLは、オープンソースのリレーショナルデータベース管理システム（RDBMS）。
- 商用DBに劣らない機能と拡張性を持ち、多くのWebアプリケーションやデータ分析基盤で広く使われている。

## 2. 特徴と強み

### 2.1. 特徴

- オープンソース
  - 無償・商用利用OK・ソースコード改変可
- 標準SQL準拠
  - ANSI SQLに準拠したクエリ構文で高い互換性
- 拡張性が高い
  - ユーザー定義関数・型・演算子・言語（PL/pgSQLなど）を自由に追加可能
- ACIDトランザクション対応
  - 高い信頼性を確保（Atomicity, Consistency, Isolation, Durability）
- JSONや全文検索に対応
  - jsonb, pg_trgm, tsvector などNoSQL的機能も充実

### 2.2. 強み

- 標準SQL対応が厳密：Oracle互換を求めるシステムにも向く
- CTE、ウィンドウ関数、jsonb、配列、ENUM など高機能
- 拡張性が高い：演算子・関数・集約関数・型を自作可能
- 複雑なクエリでもパフォーマンスが出やすい（EXPLAINの出力も豊富）
- 商用DBに迫る機能がOSSで使える（例：トリガー、全文検索、論理レプリケーション）

## 4. 実行計画（EXPLAIN）の基礎

### 4.1. 基本の見方

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

- 上から下ではなく、**インデントが一番深い（内側の）ノードから実行される**
- `cost=開始コスト..合計コスト`、`rows=見積もり行数`、`actual time=実測時間`を見比べる
- 見積もり`rows`と`actual`が大きくズレていたら統計情報が古いサイン（`ANALYZE`推奨）
- 遅いクエリの原因は大抵「本来Index Scanになるべきところが Seq Scan になっている」か「JOINの方式が非効率」のどちらか

### 4.2. スキャン方式（テーブルの読み方）

| 名前 | 動作 | 使われる場面 |
| --- | --- | --- |
| Seq Scan（順次スキャン） | テーブルを先頭から1行ずつ全部読む | インデックスがない、または該当行がテーブルの大半を占める場合 |
| Index Scan | インデックスで該当行の場所を特定してから本体データ（ヒープ）を読みに行く | 絞り込み条件で少数の行だけがヒットする場合 |
| Index Only Scan | インデックスだけで完結し本体データを読みに行かない（SELECT列が全てインデックスに含まれる場合） | Index Scanよりさらに高速 |
| Bitmap Heap Scan | インデックスで該当ページの地図（ビットマップ）を作り、まとめて読みに行く | 該当行がそこそこ多い（Index Scanほど少なくないがSeq Scanほど多くない）中間的な場合 |
| Parallel Seq Scan | Seq Scanを複数のワーカープロセスに分担させる | テーブルが大きく、単純な全件走査で並列化のメリットがオーバーヘッドを上回る場合 |

### 4.3. JOINの方式

| 名前 | 動作 | 得意な場面 |
| --- | --- | --- |
| Nested Loop | 片方の各行に対し、もう片方を毎回検索 | 片方が少数行かつインデックスが効く |
| Hash Join | 片方をハッシュテーブル化し、もう片方と突き合わせ | 中〜大規模データ同士の等価結合 |
| Merge Join | 両方をソート済みにして順番に突き合わせ | 既にソート済み、またはソートコストが低い場合 |

### 4.4. Parallel Query（並列クエリ）

PostgreSQL 9.6以降で導入。Seq Scanに限らず、集約やJOINの一部も複数バックエンドプロセス（ワーカー）に分割して並列実行できる。

- `EXPLAIN`で `Gather` ノードの下に `Parallel Seq Scan` 等が出ていれば並列実行されている（`Gather`がワーカーの結果をリーダープロセスにマージする）
- 並列度は `max_parallel_workers_per_gather` などの設定で決まる
- プランナーは `parallel_setup_cost`（並列化を始めるコスト）と `parallel_tuple_cost`（行をワーカー間でやり取りするコスト）を見積もり、通常のSeq Scanより有利と判断した場合のみ並列化する
- テーブルが小さい、または`WHERE`/`LIMIT`で処理対象行数が少ないと判断されると、並列化のオーバーヘッドの方が大きいとみなされ通常のSeq Scanのまま実行される
- 単純な`SELECT`で結果セットがそのまま大きい場合より、`count`や`sum`などの集約、大規模テーブル同士のJOINと組み合わせた方が効果が出やすい
