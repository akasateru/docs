# 認証認可

## 1. HMAC

- Hash-based Message Authentication Code
- メッセージ認証コード（MAC）の１つ

下記を保証する

1. メールの送信者が第三者のなりすましでないか
2. メッセージが改竄されていないか

## 2. セキュリティ対策

### 2.1. クレデンシャル強化

- シークレットの載せ方
  - URL より Authorization / 専用ヘッダ に寄せる（ログ・Referer 漏えい対策）。
- キーの種類の分離
  - ブラウザ用とサーバー用でキー／スコープを分ける、サーバー用のみ 強い操作を許す、など。
- ローテーション・失効
  - 漏えい時の手順と、定期的な入れ替え。
- レート制限・異常検知
  - キー／IP 単位のスロットリング、監視。

### 2.2. トークンベース

- 短命アクセストークン
  - 長寿命の API キーはバックエンドだけが保持し、外向きは 短命 Bearer のみ、など。
- OAuth 2.0 Client Credentials
  - サーバー間の定番。実装は 認可サーバー＋プロダクト または API Gateway に寄せるパターンが多い。
- JWT の検証
  - 自前または IdP が発行し、署名・有効期限・audience を API 側（またはゲートウェイ）で検証。

### 2.3. ネットワーク・エッジ

- IP 許可（WAF / LB / Cloud Armor 等）
  - 固定出口が取れる場合に有効。テナントごと にやるかは設計次第。
- Private 接続 / 内部 LB
  - インターネットに URL を出さない構成。要件・コストは上がりがち。
- mTLS
  - クライアント証明書で「このサーバーから」まで縛る。運用負荷は高め。

サーバー間連携では、API キー／シークレットの扱いに加え、必要に応じて短命トークン・OAuth（M2M）・IP 制限・BFF／ゲートウェイ・閉域など、ブラウザに依存しない層での対策を組み合わせるのが一般的

## 3. Basic認証とBearer認証

HTTPの`Authorization`ヘッダーで送る認証情報の代表的な2方式。「何をどう証明するか」という軸で対比すると整理しやすい。

- **Basic認証**: `ユーザー名:パスワード` を Base64 エンコードして毎リクエスト送る。Base64 は暗号化ではなく単なる変換（誰でも容易に復元可能）なので、必ず HTTPS が前提。仕組みが単純な分、社内システムなど限定的な場面で使われる。
- **Bearer認証**: `Bearer` = 「持参人」の意。パスワードそのものではなく、**一度発行された「トークン」を持っていること自体が証明になる**方式。
  - `Authorization: Bearer eyJhbGc...` の形式で送る。
  - トークンが漏えいすると本人になりすまされるため、有効期限・失効の仕組みとセットで使う。
  - API 開発で見るトークンは多くの場合 **JWT**（JSON Web Token）で、ユーザー ID や有効期限などの情報を含み、署名で改ざんの有無を検証できる。
  - **OAuth 2.0** は、この Bearer トークンを安全に発行するための手順を定めた規格（「Google でログイン」など）。ログインの結果としてトークンが発行され、以降の API 呼び出しではそのトークンを使う。
- 関連する他の方式:
  - **API キー**: 固定の長いランダム文字列で呼び出し元を識別する。Bearer トークンと同じく「持っていれば証明になる」方式（Anthropic/OpenAI の API キーなど）。
  - **セッション/Cookie 認証**: ログイン後にサーバーがセッション ID を発行し、ブラウザが Cookie として自動送信する方式。従来の Web アプリのログイン状態維持で使われる。
  - **mTLS**: 共有された秘密ではなく、クライアント側の証明書で暗号的に証明する方式。より強固だが運用負荷は高い。

整理すると、Basic ＝ 毎回パスワードを送る／Bearer・API キー・Cookie ＝ 一度発行されたものを持っていることで証明／mTLS ＝ 証明書で暗号的に証明、という軸で分類できる。
