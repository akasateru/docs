# 1. デプロイ戦略

本番環境へ新バージョンを反映する際のリリース手法。ダウンタイムやリスクをどう抑えるかで手法が分かれる。

## 1.1. カナリアリリース

新バージョンを**一部のユーザー・トラフィックにだけ先行公開**し、問題がないか監視しながら段階的に展開範囲を広げていく手法。名前は「炭鉱のカナリア」（異常があれば真っ先に反応する）に由来する。

### 1.1.1. 基本的な流れ

1. 新バージョンを本番環境に少数のインスタンスだけデプロイ
2. トラフィックの一部（例: 5%）だけを新バージョンに振り分け
3. エラー率・レイテンシ・ビジネス指標などを監視
4. 問題なければ徐々に比率を上げる（5% → 25% → 50% → 100%）
5. 問題があれば即座に旧バージョンへロールバック

### 1.1.2. メリット

- **ブラスト半径が小さい**: 不具合があっても影響を受けるユーザーが限定的。
- **本番データでの検証**: ステージング環境では気づけない問題（実トラフィックのパターン、スケール起因の問題など）を検出しやすい。
- **ロールバックが容易**: 全体切り替え前なので、影響範囲が小さいうちに戻せる。

### 1.1.3. デメリット・注意点

- 新旧バージョンが同時に稼働するため、**DBスキーマやAPIの後方互換性**を保つ必要がある。
- 適切な**モニタリング・アラート**がないと効果が薄い（異常を検知できなければ「カナリア」の意味がない）。
- ステートフルな処理（セッション等）がある場合、同一ユーザーが新旧を行き来しないよう配慮が必要。

### 1.1.4. 実装例

- **Kubernetes**: [Argo Rollouts](https://argoproj.github.io/rollouts/)、[Flagger](https://flagger.app/) などのツールでカナリア戦略を宣言的に管理（→ [Kubernetes.md](Kubernetes.md)）。
- **サービスメッシュ（Istio等）**: `VirtualService` でトラフィック比率を柔軟に制御（→ [サービスメッシュ.md](サービスメッシュ.md)）。
- **AWS**: CodeDeploy のカナリアデプロイ設定、ALB + 重み付けターゲットグループ。
- **GCP**: Cloud Deploy のカナリア戦略、Cloud Run のトラフィック分割機能（→ [Cloud Run.md](../../Cloud/GCP/Cloud%20Run.md)）。

### 1.1.5. LLM系サービスでの応用

新プロンプトや新モデルを一部リクエストにだけ適用し、応答品質や評価指標（LLM-as-a-Judge等）を比較してから全展開する、という形でも同じ考え方が使える。

## 1.2. Blue-Greenデプロイとの比較

| | カナリア | Blue-Green |
|---|---|---|
| 切り替え | 段階的（比率を徐々に増加） | 一括切り替え |
| リスク | 小さく限定的 | 切り替え時に全ユーザーへ一気に影響 |
| 複雑さ | ルーティング制御が必要でやや複雑 | 比較的シンプル（環境を丸ごと切り替えるだけ） |
| ロールバック | 比率を戻すだけ | 旧環境（Blue）に向き先を戻すだけで即時 |
