# フロントエンド・バックエンドの配信アーキテクチャ

DNSからアプリへの接続方法と、同一ドメインでフロントエンド（静的ファイル）とバックエンド（API）を両立させる代表的な構成パターンをまとめる。

## 1. DNSとアプリの接続

DNSは「ドメイン名 → IPアドレス」の対応表でしかなく、それ自体はアプリを配信しない。実際に繋ぐには手前に固定IPを持つ受け口（ロードバランサ等）が必要。

```
1. アプリの前にロードバランサを置く（GCSバケット等それ自体には固定IPが無いため）
2. ロードバランサに固定のグローバルIPが割り当てられる（例: 34.120.10.5）
3. DNSにAレコードを設定: example.com → A → 34.120.10.5
4. ユーザーが example.com にアクセス → DNSがIPを返す → ロードバランサ経由でアプリに到達
```

VercelやFirebase Hostingなどマネージドなホスティングを使う場合は、相手側のIPが変わる可能性があるため、IPを直接指定するAレコードではなく**CNAMEレコード**（ドメイン → 別ドメイン名のエイリアス）を使うのが一般的。相手側でIPが変わっても自分のDNS設定を変えずに済む。ただし**ルートドメイン（`example.com`自体）にはCNAMEを設定できない**（他のレコード種別と共存できないというDNSの仕様上の制約）ため、ルートドメインを使いたい場合は「CNAME的に振る舞うAレコード」（CloudflareのCNAME Flattening、AWSのALIASレコードなど）を使うことが多い。DNSレコード種別の一覧は[Network](../Network/Network.md)を参照。

## 2. 同一ドメインでフロント/バックを両立させる3パターン

「同じURLでフロントエンド（静的ファイル）とバックエンドAPIの両方にアクセスできる」のは、同じサーバーが両方処理しているのではなく、**手前の振り分け役（ロードバランサ／リバースプロキシ）がパス（`/api/*`等）を見て転送先を変えている**ため。

### 2.1. パターンA: 別サービス + パスベースルーティング（推奨）

```
[DNS] → [Load Balancer / URL Map]
           ├── /        → フロントエンド（静的ファイル、GCS/Vercel等）
           └── /api/*   → バックエンド（Cloud Run等）
```

フロントとバックが完全に独立してデプロイ・スケールできる。GCPなら`google_compute_url_map`でパスルールを設定する。

### 2.2. パターンB: バックエンドが静的ファイルも配信

```python
# 例: FastAPI
app.mount("/", StaticFiles(directory="dist", html=True), name="static")

@app.get("/api/users")
def get_users(): ...
```

デプロイ先が1つで済み構成がシンプル。小規模・個人開発向き。デメリットは[3. パターンBのデメリット](#3-パターンbのデメリット)を参照。

### 2.3. パターンC: フルスタックフレームワークに寄せる（Next.js等）

```
Next.jsの中に:
  - pages/ or app/       → フロントエンド（React）
  - app/api/*/route.ts   → バックエンドAPI（Route Handlers）
```

Node.js/TypeScript前提になるため、Python（FastAPI等）の資産を使いたい場合は不向き。

### 2.4. 選定の目安

| 状況 | 推奨 |
| --- | --- |
| バックエンドをPython等で書きたい | パターンA（本番） or B（簡易） |
| フロント・バックを別チーム/別リポジトリで管理したい | パターンA |
| 個人開発・小規模で構成をシンプルにしたい | パターンB |
| フルスタックをTypeScriptで統一したい | パターンC |

同一ドメイン配下の別パスに分けることで、別ドメイン（`app.example.com`と`api.example.com`）に分けた場合に必須になるCORS設定が不要になり、Cookie（認証情報等）もそのまま共有できる。

## 3. パターンBのデメリット

バックエンド（例: Cloud Run）が静的ファイルとAPIの両方を1サービスで配信する構成の主な問題点。

- **スケーリングが結合している**: 静的ファイル配信（軽い）とAPI処理（重い可能性）が同じコンテナ・同じスケーリング設定を共有し、静的ファイルへのアクセス増だけでAPIと同じ台数までスケールしてコストが余分にかかる。
- **CDNキャッシュが効かない**: GCS+Cloud CDNやFirebase Hostingは静的ファイルをエッジにキャッシュするが、Cloud Run単体だと毎回コンテナまでリクエストが届き、JS/CSSの配信のたびに課金対象のリクエストが発生する。
- **コールドスタートがフロントにも影響する**: Cloud Runが0スケールしている状態だと、APIだけでなくトップページの初回表示すら遅延する（コンテナ起動待ち）。
- **デプロイが結合している**: CSSの微修正だけでも、バックエンドの依存関係含めて全体を再ビルド・再デプロイする必要があり、フロントとバックのリリースサイクルを分けられない。

トラフィック規模や更新頻度次第では問題にならないケースもあり、必ずしも即座に改善が必要というわけではない。

## 4. Firebase Hosting

Googleが提供する静的ファイル専用のホスティングサービス。GCSを直接使うより設定が簡単で、以下が最初から組み込まれている。

- 世界中のCDNエッジからの配信（自動）
- 無料SSL証明書の自動発行・更新
- カスタムドメインの接続がシンプル（CNAME数行）
- SPA用の「全部`index.html`に返す」設定がconfig一行

```json
// firebase.json
{
  "hosting": {
    "public": "dist",
    "rewrites": [
      { "source": "**", "destination": "/index.html" }
    ]
  }
}
```

`rewrites`に`run`設定を追加すると、GCPのLoad Balancerを自前で組まなくても**パターンAのパスベースルーティング**を実現できる。

```json
{
  "hosting": {
    "public": "dist",
    "rewrites": [
      { "source": "/api/**", "run": { "serviceId": "my-backend", "region": "asia-northeast1" } },
      { "source": "**", "destination": "/index.html" }
    ]
  }
}
```

構成の変更イメージ（パターンB → パターンA相当）:

```
今:
[DNS] → [Cloud Run（静的ファイル + API 両方）]

改善後:
[DNS] → [Firebase Hosting]
           ├── /        → dist/（静的ファイル、CDN配信）
           └── /api/**  → [Cloud Run（APIのみ）]
```

FastAPI側の`StaticFiles`マウントを外してAPI専用にし、`dist/`をFirebase Hostingにデプロイするだけなので、パターンBからの移行の手間は比較的小さい。
