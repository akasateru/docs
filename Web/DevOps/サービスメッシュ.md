# 1. サービスメッシュ

マイクロサービス間の通信を管理するインフラ層。アプリケーションのコードを変更せずに、サービス間通信の制御・可視化・セキュリティを一元的に扱える。

## 1.1. 解決する課題

マイクロサービス化が進むと、サービスの数だけ「どこに接続するか」「失敗時のリトライ」「通信の暗号化」といった関心事が各サービスに個別実装されがちになる。これをアプリケーションコードから切り離し、インフラ側で共通に扱えるようにするのがサービスメッシュの狙い。

## 1.2. 仕組み（サイドカーパターン）

各サービスの隣に**サイドカープロキシ**（例: Envoy）を配置し、サービス同士は直接通信せず必ずサイドカー経由でやり取りする。

```text
[サービスA] ⇄ [サイドカーA] ⇄ [サイドカーB] ⇄ [サービスB]
```

- **データプレーン**: 実際の通信を中継するサイドカープロキシ群。
- **コントロールプレーン**: サイドカー群にルーティングルールやポリシーを配信・管理する司令塔。

## 1.3. 主な機能

| 機能 | 内容 |
| --- | --- |
| トラフィック管理 | ロードバランシング、カナリアリリース、A/Bテスト用のルーティング |
| 可観測性 | サービス間通信のメトリクス・トレース・ログを自動収集 |
| セキュリティ | mTLS（相互TLS）によるサービス間通信の自動暗号化・認証 |
| 耐障害性 | リトライ、タイムアウト、サーキットブレーカーの共通化 |

## 1.4. 代表的な実装

- Istio: 最も広く使われる、Kubernetes上で動く高機能なサービスメッシュ。
- Linkerd: 軽量・シンプルさを重視した実装。
- Consul Connect（HashiCorp）
- AWS App Mesh: AWS環境向け。

## 1.5. 注意点

強力な反面、サイドカーの追加でレイテンシやリソース消費が増え、運用の複雑性も上がるトレードオフがある。サービス数が少ない小規模構成では過剰投資になりやすく、「マイクロサービスが一定規模に達してから導入を検討する」のが実務上の一般的な判断基準。クラウドネイティブが前提化する流れの中で標準ツール化しつつある（[[技術トレンドのキャッチアップ]]）。
