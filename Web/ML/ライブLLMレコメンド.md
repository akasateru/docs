ユーザーの直近の行動をその場でLLMのプロンプトに組み込み、リクエスト都度リアルタイムに推薦を生成する手法。従来のバッチ型レコメンド（[[協調フィルタリング]]など）と対比される。

## 1. ライブLLMレコメンドとは

- 「ライブ」は主に**リアルタイム・パーソナライズ**の意味で使われる。ユーザーが今まさに取った行動（クリック、検索クエリ、閲覧中の商品、直近の会話内容など）をその場でプロンプトに詰め込み、LLMがリクエストごとに文脈を読んで推薦理由も含めて動的に生成する
- 「なぜこれを勧めるか」を自然文で説明できる（説明可能性が高い）のが最大の特徴

## 2. 従来のバッチ型レコメンドとの違い

| 観点 | バッチ型（協調フィルタリング等） | ライブLLM型 |
|---|---|---|
| 学習/計算タイミング | 過去ログをオフラインでまとめて処理、更新は数時間〜1日単位 | リクエスト都度オンザフライで生成 |
| コールドスタート | 弱い（評価データがないと推薦できない） | 強い（埋め込み学習を待たず文脈だけで推薦できる） |
| 説明性 | 低い（潜在因子に明示的な意味がない） | 高い（推薦理由を自然文で生成できる） |
| コスト・レイテンシ | 低い（事前計算済み） | 高い（推論が都度走る） |

- 大規模サービスでは両者のハイブリッドが主流：**候補生成はバッチ/軽量モデル、最終ランキングと理由付けだけライブLLM**という役割分担でコストとレイテンシのバランスを取る

## 3. アーキテクチャ全体像

```
イベント収集（Kafka）
   → 特徴量ストア（Redis）
   → ベクトル検索で候補絞り込み（Vector DB）
   → LLMで最終ランキング＋理由生成（Claude API等、prompt caching）
   → ストリーミングでUIに返却
```

## 4. 各コンポーネントの技術

### 4.1. リアルタイム特徴量収集

- **Kafka / Kinesis**: ユーザーの行動イベントをストリームで収集
- **Redis / Feature Store（Feastなど）**: 直近の行動を低レイテンシで取り出せるように保持

#### 4.1.1. Kafkaとは

- 分散イベントストリーミングプラットフォーム。Producer（送信側）とConsumer（受信側）が疎結合のまま、大量イベントを高スループットでやり取りできる
- 直接DBに書き込むと書き込み負荷やレイテンシがボトルネックになるため、間にKafkaを挟むことで非同期化・複数消費者への同時配信・バッファリング（下流が落ちてもイベントを保持できる）が可能になる
- 用語: **Topic**（イベント種別ごとのチャンネル、例 `page-view`）、**Producer**（送信側）、**Consumer**（受信側）、**Partition**（Topicを分割して並列処理・スケールさせる単位）

#### 4.1.2. Pub/Subとの違い

Kafkaは広義には「Pub/Sub」の一種（Publisherが送信、Subscriberが購読する疎結合モデルは共通）だが、一般的なPub/Sub（GCP Pub/Subなど）とは性質が異なる。

| 観点 | Kafka | 一般的なPub/Sub |
|---|---|---|
| メッセージの扱い | 一定期間ログとして保持され、Consumerは好きな位置（Offset）から読み直せる | 配信したら消える（保持期間は延長可能だが思想が違う） |
| 順序保証 | Partition内で順序が保証される | 保証されないことが多い |
| 読み取り方式 | Pull型（Consumerが自分でOffsetを管理して取りに行く） | Push型（サーバーがConsumerに配信）が多い |
| 用途の重心 | 大量イベントのストリーム処理基盤（ログ的性質） | 単発通知・非同期タスクキュー |

- イメージ: 一般的なPub/Subは「郵便配達」（配ったら終わり）、Kafkaは「録画済みラジオ番組」（過去に遡って何度でも聞き直せる）
- この「後から読み直せる」性質により、例えば特徴量ストアがダウンしていた間のイベントを復旧後にまとめて再処理する、といった運用がしやすい

### 4.2. 候補生成（Retrieval）

- **ベクトルDB**（Pinecone, Weaviate, Qdrant, pgvectorなど）: 商品・コンテンツの埋め込みを持ち、類似検索で候補を絞る
- **埋め込みモデル**（OpenAI embeddings, Voyage AI, Cohere embedなど）: ユーザー文脈や商品説明をベクトル化

### 4.3. LLM推論（生成・ランキング・理由付け）

- **Claude API / GPT API**: プロンプトに「ユーザー文脈＋候補リスト」を詰め込み、最終的な並び替えや推薦コピーを生成
- **プロンプトキャッシング**（Claudeのprompt caching等）: システムプロンプトや商品カタログなど固定部分をキャッシュしてコスト・レイテンシを削減
- **Structured Output / Tool Use**: LLMの出力をJSON等で構造化し、後段システムに渡す

### 4.4. 低レイテンシ配信

- 非同期処理＋ストリーミングレスポンスでLLM生成の完了を待たせずUIに逐次表示
- エッジキャッシュで、似た文脈のリクエストは結果を再利用

### 4.5. 評価・実験

- A/Bテスト基盤でバッチ推薦とライブLLM推薦の効果を比較
- LLM-as-judgeで、生成された推薦理由の品質を自動評価
