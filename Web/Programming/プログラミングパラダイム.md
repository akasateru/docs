## 1. プログラミングパラダイム

- 「データと処理をどう組み立てるか」という設計思想の分類。
- 主要な4つ: 手続き型・オブジェクト指向・関数型・宣言型。
- 多くの言語（Python、Ruby、Scalaなど）はどれか1つに縛られない「マルチパラダイム言語」で、同じ処理を複数のスタイルで書ける。

### 1.1. 手続き型（Procedural）

- 処理を上から順に実行し、データと処理が分離している。
- グローバルなデータを関数が直接操作する。

```python
items = [{"name": "apple", "price": 100}, {"name": "banana", "price": 150}]
total = 0
for item in items:
    total += item["price"]
```

### 1.2. オブジェクト指向（Object-Oriented）

- **データ（状態）と、それを操作する処理（振る舞い）を1つのオブジェクトにまとめる**考え方。
- 3つの柱。
  - **カプセル化**: データを外から勝手にいじれないよう隠し、メソッド経由でのみ変更させる。
  - **継承**: 共通部分を親クラスにまとめ、差分だけを子クラスで書く。
  - **ポリモーフィズム**: 同じ呼び出し方でも、実体（サブクラス）によって振る舞いが変わる。

```python
class Cart:
    def __init__(self):
        self.items = []

    def add(self, name, price):
        self.items.append({"name": name, "price": price})

    def total(self):
        return sum(item["price"] for item in self.items)
```

### 1.3. 関数型（Functional）

- 状態を変更しない「純粋関数」（同じ入力には常に同じ出力を返し、副作用がない関数）を組み合わせて処理を組み立てる考え方。
- 本質は「`class`構文があるかどうか」ではなく「**副作用の有無・データの不変性**」。関数型言語にもクラスやデータ型は存在する（Haskellの`data`型、Scalaの`class`など）。逆に`class`を使っていても、状態を書き換えず新しい値を返すメソッドだけで構成すれば関数型的な書き方になる。

```python
from functools import reduce

total = reduce(lambda acc, item: acc + item["price"], items, 0)
```

### 1.4. 宣言型（Declarative）

- 「どう処理するか（手順）」ではなく「何が欲しいか（結果）」を書く。
- SQL、HTML、設定ファイル（Terraform、ルーティングDSLなど）もこの一種。

```python
total = sum(item["price"] for item in items)
```

### 1.5. パラダイムの判断材料

実プロジェクトのコードは複数パラダイムが混在するのが普通。「プロジェクト全体が何パラダイムか」よりも「このファイル/処理はどのパラダイムか、なぜそう言えるか」を具体的に見るのが実用的。

| パラダイム | コードに現れる特徴 |
| --- | --- |
| 手続き型 | トップレベル関数の羅列、グローバル変数、上から下への逐次実行 |
| オブジェクト指向 | `class`定義、継承、インスタンス変数、カプセル化（private/public） |
| 関数型 | 状態を変更しない関数、`map`/`filter`/`reduce`、イミュータブルなデータ |
| 宣言型 | 「どうやるか」ではなく「何が欲しいか」を書く（SQL、設定ファイル） |

### 1.6. 言語ごとの違い（Ruby vs Python）

- **Ruby**: すべての値（数値・文字列・nil含む）が何らかのクラスのインスタンスで、最終的に`Object`クラスを継承している。`freeze`/`frozen?`は`Object`クラスに定義されたインスタンスメソッドなので、継承の結果としてどんなオブジェクトでも使える。つまり「`freeze`が使える」＝「このコードがオブジェクト指向的に設計されている」ことの証明にはならない。言語仕様として最初から備わっているだけ。
- **Python**: `class`を使わずに関数型・宣言型のスタイルだけで書けてしまうため、「`class`があるかどうか」がオブジェクト指向を使っているかの分かりやすい判断材料になる（Rubyより境界がはっきりしている）。

## 2. 不変性（イミュータブル）

- 一度作った値を**後から書き換えられない**性質。オブジェクト指向とは独立した設計判断の軸。
- 目的: 「いつの間にか誰かが値を書き換えていた」という副作用由来のバグを構造的に防ぐこと。特に複数の処理（スレッドや関数）が同じオブジェクトを共有するときに効果を発揮する。
- 実現方法の例。
  - Ruby: `object.freeze`で凍結、`object.frozen?`で判定。
  - Python: `@dataclass(frozen=True)`で属性の書き換えを禁止。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: int
    y: int

def move(point: Point, dx: int, dy: int) -> Point:
    return Point(point.x + dx, point.y + dy)  # 元のpointは変更せず、新しいPointを返す
```

- 対してミュータブル（可変）な設計は、メソッド内で自身の状態を直接書き換える。

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def move(self, dx, dy):
        self.x += dx  # 自分自身の状態を書き換えている（副作用）
        self.y += dy
```

## 3. 抽象化とSOLID原則（OOP設計の指針）

- OOPの4本柱は実務上「抽象化 → 継承 → ポリモーフィズム → カプセル化」の一連の流れとして繋がっている。
  - **抽象化**: 共通の振る舞いだけをインターフェース/抽象クラスとして定義する。
  - **継承**: その抽象を実装するクラス群を作る。
  - **ポリモーフィズム**: 抽象の窓口越しに呼び出すことで、呼び出し側が具体的な型を意識しなくてよくなる。
  - **カプセル化**: 各実装クラスの内部詳細を隠す。
- 継承は「is-a関係」が成立しないと壊れやすい（fragile base class problem）。有名な反例が「正方形は長方形の一種」として`Square`を`Rectangle`から継承させるケースで、`Rectangle`の「幅と高さを独立に変更できる」という前提が`Square`では成り立たず、置き換えると壊れる。実務では「is-a」でなければ継承よりコンポジション（オブジェクトを部品として持つ）を優先する原則（"Favor composition over inheritance"）が広く支持されている。
- SOLID原則は、この4本柱を実務でどう適用すれば壊れにくい設計になるかの指針。詳細は[SOLID原則](../設計/SOLID原則.md)参照。

## 4. DSL（ドメイン固有言語）

- **DSL（Domain-Specific Language）**: 特定の目的・領域に特化した言語。対義語は**GPL（General-Purpose Language）**（Python、Javaなど何でも書ける汎用言語）。
- 例: SQL（データ操作）、HTML/CSS（文書構造）、正規表現（文字列パターン）、Terraform HCL（インフラ定義）、Google Cloud WorkflowsのYAML定義（API呼び出しの順序制御）。
- **ワークフローオーケストレーションDSLとFPの違い**: Cloud Workflowsのようなオーケストレーション系DSLは「ステップの出力を次の入力に流す」構造が関数合成に似て見えるが、本質は外部API呼び出しという**副作用の連続**を扱うものであり、FPが目指す「副作用の排除・純粋関数の合成」とは異なる。強いて言うなら、Haskellの`IOモナド`（副作用を順番に並べて実行する仕組み）に近い性質を宣言的なDSLとして表現したものと捉えるのが正確。可変な`variables`や`for`ループなど命令型の要素も普通に含む。
