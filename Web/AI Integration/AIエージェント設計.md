# AIエージェント設計

「エージェンティックAI（Agentic AI）」の概念整理と、実務でエージェントを設計する際の判断基準・アーキテクチャパターンをまとめる。

## 1. エージェンティックとは何か

LLMの利用形態は3段階に分けられる。

| 段階 | 呼び方 | 特徴 |
|---|---|---|
| 1回のAPI呼び出し | 単純なLLM利用 | 分類・要約・抽出など、1リクエスト1レスポンスで完結 |
| コードが制御するマルチステップ | ワークフロー | 開発者がループやルーティングのロジックを書く |
| モデル自身が次の行動を決める | **エージェント** | 「ツールを呼ぶか」「続けるか」「終わるか」をモデルが都度判断 |

「エージェンティック」とは、この3段目——**制御フローの決定権がコードではなくモデル側にある**状態を指す。エージェントか否かは技術というより設計判断であり、タスクが事前に手順化できるならワークフローで十分。エージェントはオープンエンドな探索が本当に必要なときだけ使うべき、コストの高い選択肢。

### 1.1. エージェントを作るべきかの判断基準

流行っているからといって何でもエージェント化するのは悪手。以下4つの基準で、1つでも「No」なら単純なAPI呼び出しやワークフローに留めるべき。

1. **複雑性**: タスクが多段階で事前に手順化しきれないか
2. **価値**: コスト・レイテンシの増加に見合う成果か
3. **実現可能性**: モデルがそのタスク種別を実際に得意か
4. **誤りのコスト**: テストやレビューで事後に回復可能か

## 2. 核となるループ構造

エージェントの内部は本質的に以下のループ。

```
while response.stop_reason == "tool_use":
    tool_result = execute(response.tool_calls)
    response = llm.call(history + tool_result)
```

これを誰が書くかで実装方式が分かれる。

- **手動ループ**: 開発者が全部書く。制御したい時に向く
- **Tool Runner的な仕組み**: SDKがループを肩代わりし、開発者はツール関数だけ書く
- **サーバー管理型エージェント（Managed Agents等）**: ループもツール実行用のサンドボックス（ファイル操作・コード実行環境）もプロバイダ側がホストする。長時間稼働やスケジュール実行に向く

## 3. ツールの2種類とMCPの役割

- **クライアント定義ツール**: 開発者が定義し、開発者のインフラで実行（DB検索、社内API呼び出しなど）
- **サーバーサイドツール**: プロバイダのインフラ上で実行される組み込みツール（Web検索、コード実行など）。レスポンス内に結果がそのまま返ってくる

ツールの数が増えると、毎リクエストでツール定義全部をモデルに見せるコストが無視できなくなる。対処法として、必要なツールだけ遅延ロードする「ツールサーチ」や、外部システムとの接続を標準化する **MCP（Model Context Protocol）** がある。MCPサーバーという共通インターフェースを介することで、どのエージェントからも同じMCPサーバーに接続でき、「エージェントの数×ツールの数」の組み合わせ爆発を防げる。詳細は[MCP.md](./MCP.md)参照。

## 4. コンテキスト管理

エージェンティックなタスクが長く続くと、会話履歴（特にツール実行結果）が肥大化し、コンテキストウィンドウを圧迫する。対処法は目的によって異なる。

- **プロンプトキャッシング**: 同じプレフィックスを再利用してコスト・レイテンシを削減（安定した内容を前に、変動する内容を後ろに置くのが鉄則）
- **コンパクション**: 古い履歴をサーバー側で自動要約
- **コンテキスト編集**: 古いツール結果だけを消去（要約ではなく削除）
- **メモリツール**: セッションをまたいで必要な情報だけ保持

どれを使うかはタスクの性質次第で、「とにかく全部残す」設計は高コスト・低速になりがち。

## 5. マルチエージェント協調

### 5.1. なぜ単一エージェントでは足りなくなるか

単一エージェントが抱える典型的な限界は**コンテキストの汚染**。複数のソースを調査する、大量のファイルを1件ずつ処理する、といったタスクでは、読み込んだ情報がすべて同じコンテキストウィンドウに蓄積され、本来の判断に使うべき「頭」が調査メモで埋まってしまう。マルチエージェント構成は、この「読み込み・調査」と「判断・統合」を別々のエージェントに分離することで解決する。

### 5.2. 基本パターン

- **Orchestrator-Worker（指揮官-作業者）**: 上位エージェント（オーケストレーター）がタスクを分解し、下位のワーカーエージェントに委譲、結果を受け取って統合する。最も一般的で扱いやすい
- **セルフコピー型**: 最初は複雑な役割分担を設計せず、「自分自身のコピーに委譲できる」状態からスタートし、後から専門化したワーカー（読み込み専用の安いモデルなど）を追加していく、インクリメンタルな作り方が実務的に推奨される
- **レビュー・検証ペア**: 1つのエージェントが成果物を作り、別のエージェント（または同じモデルの別インスタンス）がレビューする。コード生成→コードレビュー、ドラフト作成→ファクトチェックなど品質担保に使われる

### 5.3. モデル選択とコスト設計

| 役割 | 求められる能力 | モデル選択の指針 |
|---|---|---|
| オーケストレーター | 全体計画、優先順位判断、最終統合 | 高性能モデル（判断の質が成果物の質に直結するため） |
| ワーカー | 情報収集、単純作業、定型処理 | 安価なモデル（並列実行するため1件あたりのコストが積み上がる） |

「全部同じ高性能モデルで統一する」のは一見シンプルだが、ワーカーの作業は定型的なことが多く、安いモデルで十分な精度が出るケースが大半。コスト最適化の第一歩は、まず役割ごとにモデルを分けて測定すること。

### 5.4. 実務的な課題

1. **通信オーバーヘッド**: エージェント間でやり取りする情報量が増えるとトークンコストと待ち時間が増大する。ワーカーの生の調査結果を全部オーケストレーターに渡すのではなく、要約してから渡す設計が重要
2. **一貫性の担保**: 並列に動くワーカー同士が矛盾した結論を出すことがある。オーケストレーターが統合時に矛盾を検出・解消する責任を持つ必要がある
3. **デバッグの難しさ**: 単一エージェントより障害点が増えるため、「どのエージェントが・どの時点で・何を判断したか」をトレースできるロギングが設計段階から必須
4. **評価の複雑化**: 「個々のエージェントの精度」と「全体としての成果物の質」の両方を評価する必要がある。個々は正しくても統合がまずいと全体が崩れる、というケースが典型的な落とし穴

### 5.5. いつ使うべきか

単一エージェントで十分な精度・速度が出るなら、マルチエージェント化は複雑性とコストが増えるだけの過剰設計になる。目安は「1つのエージェントのコンテキストが調査内容だけで埋まってしまう」規模のタスクかどうか。

## 6. 常時稼働エージェント（Always-on Agent）

従来のエージェントは「ユーザーがリクエストを送る→エージェントが動く→終わる」という**リクエスト駆動**。常時稼働エージェントは、人間の指示を待たずに自律的にトリガーされ、バックグラウンドで動き続ける設計。

| 項目 | リクエスト駆動 | 常時稼働 |
|---|---|---|
| トリガー | 人間の入力 | スケジュール（cron）、イベント、外部システムの変化 |
| セッション寿命 | 短い（数分） | 長時間 or 永続的 |
| 人間の関与 | 都度確認 | 例外時のみ介入（人間はオンデマンドで呼ばれる側） |
| 状態管理 | セッション内で完結 | セッションをまたいで記憶・コンテキストを保持する必要 |

### 6.1. 設計上の論点

1. **トリガー設計**: スケジュール実行（毎晩レポート生成など）とイベント駆動（Slackメッセージ、DB変更、Webhookなど）の2系統。「エージェントが起動すべきタイミング」の判断ロジックを雑に作ると不要な起動でコストが膨らむ
2. **権限とガードレール**: 人間が都度承認する前提のワークフローと違い、常時稼働エージェントは自分で判断して行動を実行する。「どの操作は自動実行してよいか／どの操作は人間の承認を挟むか」をポリシーとして事前定義する必要がある。典型的には3段階
   - `always_allow`: 常に自動実行（読み取り専用操作など）
   - `always_ask`: 常に人間確認（破壊的操作、外部送信など）
   - `auto`: リスクをサーバー側で評価し、高リスクなら拒否、曖昧なら一時停止して人間を待つ
3. **失敗時の振る舞い**: 人間が見ていない間に失敗するので、「黙って止まる」のではなく、失敗を検知して通知する仕組み（アラート、ログ、再試行ポリシー）が必須。「日次ジョブがコケたまま誰も気づかない」という事故につながりやすいポイント
4. **コストの上限**: 人間が都度「実行していいか」を判断しない分、暴走（無限ループ、過剰なAPI呼び出し）のリスクが上がる。セッション単位・実行単位でのハードな予算上限（トークン数、ドル換算の上限）を設定しておくのが実務的な必須事項
5. **継続的な記憶**: 1回のセッションで完結しないため、「前回何をしたか」を次回の起動に引き継ぐ記憶の仕組みが必要。会話履歴をそのまま持ち越すのではなく、要点だけを永続化するメモリ層を挟むのが一般的

### 6.2. 具体例

- 毎朝ニュース・メールをチェックして要約を作る「モーニングブリーフ」的エージェント
- 本番環境のログを監視し、異常検知したらPRを自動作成するエージェント
- 社内のデータパイプラインを毎晩走らせ、異常値があればSlack通知するエージェント

## 7. 評価（Evals）の重要性

エージェンティックシステムは非決定的な振る舞いをするため、「動いているように見える」と「実際に信頼できる」の間にギャップが生まれやすい。本番投入前にevalセット（何を評価するか・採点方法・コスト）を作り、プロンプトやツール設計の変更を定量的に検証する運用が、流行を追うだけのプロトタイプと実運用の分かれ目になる。マルチエージェント構成では個々のエージェント精度と全体成果物の質の両方を評価する必要がある点に注意（5.4節参照）。

## 8. 「エージェントの次」として語られる方向性

2026年時点でエージェンティックAIの延長・次フェーズとして語られる方向性は複数あり、どれか一つに収束しているわけではない（業界全体の幻滅期トレンドについては[技術トレンドのキャッチアップ.md](../../General/技術トレンドのキャッチアップ.md) 1.4.1節参照）。

| 方向性 | 何が変わるか |
|---|---|
| **フィジカルAI / 身体性AI** | デジタル行動→物理世界での行動へ拡張（ロボティクス統合） |
| **常時稼働エージェント** | リクエスト駆動から、バックグラウンドで常時監視・自律実行する形へ（本記事6節） |
| **マルチエージェント協調・組織化** | 単一エージェントから、役割分担した複数エージェントが協調するシステムへ（本記事5節） |
| **長期記憶・パーソナライズ** | セッション単位の文脈から、人・組織ごとに蓄積される永続的な記憶へ |
| **世界モデル（World Models）** | 言語ベースの推論から、物理法則や因果関係を内部表現として持つモデルへ（フィジカルAIの基盤技術でもある） |
| **科学的発見エージェント** | 既存知識の利用から、仮説生成→実験→検証を自律的に回す研究支援へ |

フィジカルAIはデジタルと違い「失敗のコストが物理的・不可逆」という点で難易度が格段に高く、研究段階〜限定実用段階のものが大半。多くの企業にとっては、まだ今のLLM/APIの延長線上で実装可能な**常時稼働エージェント・マルチエージェント協調・長期記憶**の方が、物理ハードウェアという追加の不確実性を抱えずに先に実務インパクトを出せる領域。
