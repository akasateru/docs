# RAG

## 1. 概要

RAG（Retrieval-Augmented Generation：検索拡張生成）は、大規模言語モデル（LLM）が回答を生成する前に、社内文書やデータベースなどの外部情報を検索し、その情報を元に回答を作成する技術。

### 1.1. RAGのメリット

- **高精度・高信頼性:** 正確なソース（外部情報）に基づくため、事実に基づいた回答が可能。
- **ハルシネーションの低減:** モデルの知識だけでなく、提示された資料から回答するため虚偽情報が減る。
- **最新・固有情報の活用:** 社内規定、マニュアル、最新のWeb情報などを利用できる。
- **コスト削減:** 再学習（ファインチューニング）より低コストで独自のAIを構築できる。

### 1.2. 主な活用事例

- **社内FAQ・ヘルプデスク:** 社内規程や過去の知見を検索し、回答を作成。
- **文書要約・分析:** 長大な報告書やマニュアルの特定箇所を抽出して要約。
- **カスタマーサポート:** 製品マニュアルを参照して、正確なサポートを行う

### 1.3. RAGの技術的要素

- **ベクトルデータベース:** テキストを数値（ベクトル）化して高速に検索する仕組み（例: Pinecone, Milvus）。
- **Embeddingモデル:** テキストをベクトルに変換するモデル。
- **LLM:** 生成を担当するモデル（例: GPT-4, Claude, Llama）

## 2. 仕組み

- **検索 (Retrieval):** ユーザーの質問に関連する情報をデータベースから抽出。
- **拡張 (Augmented):** 抽出した情報（コンテキスト）をユーザーの質問に付与。
- **生成 (Generation):** LLMが付与された情報を踏まえて回答を作成。

## 3. 例

FAQの場合
1. ユーザーの質問をベクトル化　→ 検索クエリベクトル
2. FAQの各文章もベクトル化 → 文章ベクトルを事前に保存
3. 類似度計算 → コサイン類似度などで比較
4. 上位N件取得 → スコアが高い順に取得
5. コンテキスト作成 → 検索結果を結合し「情報源」として準備
6. LLMに渡す → 質問+情報源を一緒にプロンプトに入れて、LLMが回答生成

## 4. ベクトル検索の速度と近似最近傍探索（ANN）

RAGの検索ステップ（類似度計算〜上位N件取得）は、データ件数が増えると総当たり計算が重くなるため、実運用では近似最近傍探索（ANN: Approximate Nearest Neighbor）のインデックスが使われる。検索速度は「クエリと最近傍の距離」そのものではなく、**採用しているアルゴリズムとクエリ点周辺のデータ密度・分布**に依存する。

- **総当たり（brute-force / flat index）**: 全ベクトルとの距離計算を毎回行うため、最近傍が近いか遠いかに関わらず計算量は常に一定（O(n·d)）。
- **木構造（KD-tree, Ball-treeなど）による厳密最近傍探索**: 近傍が近い（密なクラスタにクエリが入る）ほど枝刈り（pruning）が効いて速くなり、疎な領域では多くの枝を辿るため遅くなる。
- **HNSW・IVFなどのANN**: クエリ点周辺の密度や、クラスタ境界に近いかどうかで探索コストが変わる。

### 4.1. HNSW（Hierarchical Navigable Small World）

Faiss, Milvus, Qdrant, pgvector など主要なベクトルDBで標準的に使われるグラフベースのANNアルゴリズム。ベクトル同士を「近いものを辺で繋いだグラフ」として構築し、クエリ時にグリーディに近い方向へグラフを辿ることで、全探索せずに近傍を見つける。

**構造（階層＝Hierarchical）**

- スキップリストに似た複数層のグラフを持つ。
- 上位層ほどノード数が少ない疎なグラフ、Layer 0（最下層）が全ベクトルを含む最も密なグラフ。
- 各ノードがどの層まで存在するかは確率的に決まる（指数分布的に上位層ほど少なくなる）。

**検索の流れ**

1. 最上層の固定エントリポイントからスタート。
2. その層内でクエリに最も近い隣接ノードへグリーディに移動し、局所最適に到達するまで繰り返す。
3. 局所最適に達したら1つ下の層に降り、同様にグリーディ探索。これをLayer 0まで繰り返す。
4. Layer 0では `efSearch` で指定した数の候補を保持しながらビームサーチ的に探索し、上位k件を返す。

上位層が「高速道路」のように長距離ジャンプに使われ、下位層で局所的に精緻化するイメージ。計算量は対数オーダー（O(log n)）に近づく。

**主要パラメータ**

| パラメータ | 効果 |
| --- | --- |
| `M` | ノードごとの最大隣接数。大きいほど精度↑、メモリ↑、構築が遅くなる |
| `efConstruction` | 構築時の探索幅。大きいほどグラフ品質↑、構築時間↑ |
| `efSearch` | 検索時の探索幅。大きいほど検索精度↑、検索速度↓ |

**弱点**

- グラフ構造を丸ごとメモリに保持する必要があり、メモリ消費が大きい（IVF系と比べて圧縮しにくい）。
- 動的な削除が苦手（辺の整合性が崩れるため、多くの実装は論理削除＋定期リビルドで対応）。
- 逐次挿入のため構築の並列化がしにくい。
