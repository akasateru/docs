## 1. アロケーションとは

プログラムの実行に必要なメモリ領域を、OSやランタイムが確保（割り当て）すること。

対義語は**デアロケーション（解放）**で、不要になったメモリ領域を返却すること。確保したまま解放し忘れると**メモリリーク**の原因になる。

## 2. 静的アロケーションと動的アロケーション

| 種類                             | タイミング         | 特徴                                                     |
| -------------------------------- | ------------------ | -------------------------------------------------------- |
| 静的アロケーション               | コンパイル時       | サイズが固定。グローバル変数など。高速だが柔軟性がない。 |
| 動的アロケーション               | 実行時             | 実行時にサイズを決定できる。柔軟だが管理コストがかかる。 |

## 3. スタック領域とヒープ領域

メモリ確保先は主に2種類。

| 領域           | 用途                                       | 確保・解放                             | 速度   |
| -------------- | ------------------------------------------ | --------------------------------------- | ------ |
| **スタック領域** | 関数呼び出し・ローカル変数                 | 関数の呼び出し・リターンで自動的に確保・解放 | 高速   |
| **ヒープ領域**   | 実行時にサイズが決まるデータ（動的確保）   | 明示的な確保・解放が必要（言語による）  | 低速   |

- スタックはLIFO（後入れ先出し）構造で管理されるため、確保・解放が単純で速い。
- ヒープは自由な順序で確保・解放されるため、管理が複雑で**メモリフラグメンテーション（断片化）**が起こりうる。

## 4. 言語ごとのメモリ管理方式

| 方式                       | 代表言語         | 概要                                                             |
| -------------------------- | ---------------- | ------------------------------------------------------------------ |
| 手動管理                   | C, C++            | `malloc`/`free`（C）、`new`/`delete`（C++）で明示的に確保・解放。 |
| ガベージコレクション（GC） | Java, Python, Go  | 不要になったオブジェクトを自動検出して解放。開発者の負担が少ない代わりにGC実行時の停止（GCポーズ）が発生しうる。 |
| 所有権システム             | Rust              | コンパイル時に所有権・借用のルールをチェックし、GCなしで安全にメモリを解放。 |

## 5. メモリリークとフラグメンテーション

- **メモリリーク**: 解放し忘れたメモリが蓄積し、使用可能なメモリが徐々に減っていく現象。
- **フラグメンテーション**: 確保・解放を繰り返すうちにヒープ領域が虫食い状態になり、空き容量の合計は十分でも連続領域が足りず確保に失敗する現象。

## 6. セグメンテーションフォールト

**セグメンテーションフォールト（Segmentation Fault, `SIGSEGV`）**とは、プロセスがアクセス許可のないメモリ領域にアクセスしようとした際にOSが発生させるエラー。

### 6.1. 発生の仕組み

- OSはプロセスごとに仮想メモリ空間を管理し、アクセス可能な領域を制限。
- 範囲外・未割り当て・保護領域への書き込みなど不正アクセスが発生すると、MMU（メモリ管理ユニット）がハードウェア例外を発生。
- カーネルが例外を検知し、プロセスに`SIGSEGV`シグナルを送信。
- デフォルトの挙動ではプロセスが強制終了し、`Segmentation fault (core dumped)`のようなメッセージが表示される。

### 6.2. 主な発生原因

C・C++などメモリを直接扱う言語で顕著。

- NULLポインタの参照外し。
- 解放済みメモリへのアクセス（use-after-free）。
- 配列・バッファの範囲外アクセス。
- スタックオーバーフロー（無限再帰など）。
- 未初期化ポインタの使用。
- 読み取り専用領域（文字列リテラルなど）への書き込み。

### 6.3. メモリ安全な言語での扱い

Python・Java・Goなどメモリ安全性が確保された言語では、アプリケーションコードレベルでは基本的に発生しない。ただし以下のケースでは起こりうる。

- C拡張ライブラリのバグ（NumPyの内部実装など）。
- FFI経由でネイティブコードを呼んだ場合。
- 言語処理系自体のバグ。

### 6.4. デバッグ手法

- `gdb`でコアダンプを解析し、クラッシュ箇所のスタックトレースを確認。
- `valgrind`（`memcheck`）でメモリ関連のバグを検出。
- AddressSanitizer（`-fsanitize=address`コンパイルオプション）でランタイム検出。
