APIやインターフェースは一度公開すると自由に変更できなくなり、後方互換性を保ちながら機能を足すたびに設計が徐々に複雑化していく。この劣化を防ぐには「最初に完璧な設計をする」よりも「変更しやすい設計にしておく」方が現実的な目標になる。

## 1. なぜ「増改築」で汚くなっていくのか

- 引数やAPIのオプションを後から追加していくと、既存の呼び出し側を壊さないために「許容する範囲」がどんどん広がっていく。
- 結果として、本来不要な分岐・オプショナル引数・特殊ケースが積み重なり、実装が読みにくくなる。
- これはNode.jsのcallback→Promise移行、Python 2→3、HTTP APIのバージョニングなど、実例が多い現象。

## 2. 「最初の設計が完璧であるべき」という考え方の限界

- 将来のユースケースを設計時点ですべて予見するのはほぼ不可能。
- そのため目指すべきは「完璧な初期設計」ではなく「変更に強い初期設計」。
- 変更に強い設計とは、拡張の入り口（バージョニング戦略、非推奨化の手順、追加のみで済む構造）をあらかじめ用意しておくこと。

## 3. 汚くなりにくくするための実践パターン

- **追加はオプショナル引数の羅列ではなくoptions object化する**: 個別の引数を増やし続けるとシグネチャが破綻するため、まとめて拡張できる構造にしておく。
- **破壊的変更はメジャーバージョンにまとめる**: 都度小さく互換性を壊すのではなく、semverのようなルールで区切って一括で整理する。
- **feature flagで新旧動作を切り替える**: 移行期間を設けて段階的に新しい挙動へ寄せる。
- **非推奨化のポリシーを先に決めておく**: 「いつ消してよいか」のルールがないと、後方互換のためのコードが無期限に残り続ける。
- **変更は基本的に追加のみ（additive-only）にする**: 既存フィールド・引数の意味を変えず、新しい表現を追加する形にすると破壊的変更を避けやすい。

## 4. バランスの取り方（トレードオフ）

- 拡張性を意識しすぎると、最初から抽象化過多になりYAGNIに反して逆に複雑な設計になることがある。
- 実務的な落とし所は「今ある要件はシンプルに実装する。ただし変更の入り口だけは塞がないようにしておく」というバランス。
- 見えている要件以上の抽象化を先回りして作り込まないことも、[[現場で役立つシステム設計の原則]]で言う「小さくまとめてわかりやすくする」設計原則と一致する。
