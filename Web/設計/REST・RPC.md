API設計における「REST」と「RPC」は、どちらもクライアント/サーバー間の通信様式だが、何を中心に設計するかという思想が異なる。

## 1. 基本的な考え方の違い

- **REST**: リソース（名詞）を中心に設計する。URLがリソースを表し、HTTPメソッド（GET/POST/PUT/PATCH/DELETE）でそのリソースへの操作を表現する。
  - 例: `GET /users/123`, `POST /users`, `DELETE /users/123/orders/5`
- **RPC**: 手続き・処理（動詞/関数呼び出し）を中心に設計する。「サーバー側の関数をリモートから呼ぶ」という発想で、操作名をそのまま呼び出す。
  - 例: `POST /getUser`, `POST /createUser`（gRPCなら `UserService.GetUser` のようなメソッド呼び出し）

代表的な技術としては、RESTは素のHTTP + JSONが主流、RPCはgRPC（Protocol Buffers）、JSON-RPC、tRPCなどがある。

## 2. HTTPメソッドの扱い

- REST: GET/POST/PUT/PATCH/DELETEの意味（冪等性・安全性）を厳密に使い分ける。
- RPC: 多くの場合POSTのみ、またはHTTP以外の独自プロトコル（gRPCなど）を使い、HTTPメソッドの意味論はあまり重視しない。

## 3. 誤解しやすいポイント

### 3.1. 「RPC = スキーマ」ではない

RPCは通信のパラダイム（考え方）であり、スキーマ（インターフェースの型定義）とは別の概念。両者が混同されやすいのは、gRPCのような主要なRPCフレームワークが「スキーマファースト」で、`.proto`ファイルのようなIDL（Interface Definition Language）から先にスキーマを定義し、そこからクライアント/サーバーのコードを自動生成する運用が一般的なため。

ただしスキーマの有無はREST/RPCの軸とは独立している。REST側にもOpenAPI（旧Swagger）というスキーマ定義の仕組みがある。

| | RPC | スキーマ |
|---|---|---|
| 正体 | 通信パラダイム | インターフェースの型定義 |
| 例 | gRPC, JSON-RPC | Protocol Buffers, OpenAPI, GraphQL SDL |
| 必須か | スキーマなしでも成立する（例: 素のJSON-RPC） | RPC以外（RESTのOpenAPIなど）でも使われる |

### 3.2. 「REST=送りっぱなし、RPC=戻り値を待つ」ではない

どちらも基本的には同期的な「リクエスト→レスポンス」の往復であり、REST側も送りっぱなしではない。

- REST: `PUT /users/123` を送れば、更新後のリソース状態（または200 OK）が返ってくる。`GET`ならリソースの表現（JSONなど）が返ってくる。
- RPC: `getUser(123)` を呼べば、ユーザーオブジェクト（関数の戻り値）が返ってくる。

本当の違いは「戻ってくるものの意味」であって、戻ってくるかどうかではない。

| | REST | RPC |
|---|---|---|
| 返るもの | リソースの状態（スナップショット） | 実行した処理の結果（関数の戻り値） |
| 発想 | 「今このリソースはこうなっている」 | 「この処理を実行した結果はこう」 |

「送りっぱなし」のイメージが当てはまるのは同期/非同期という別の軸の話。Webhookやメッセージキュー（Kafkaなど）、`202 Accepted` を返してあとでコールバックする、といった非同期パターンはRESTでもRPCでもどちらでも実装可能。

## 4. 使い分けの目安

- **REST**: 公開API、CRUD中心のWebサービス、HTTPキャッシュ機構（ETag, Cache-Controlなど）を活かしたい場合。
- **RPC**: マイクロサービス間の内部通信、パフォーマンス重視（gRPCはバイナリで高速）、単純なCRUDに収まらない複雑な操作。
