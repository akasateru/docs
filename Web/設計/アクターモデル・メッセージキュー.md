並行処理・分散システムにおける「メッセージパッシング」という発想を、スコープの異なる3つのレイヤー（プロセス内・マシン内・サービス間）で実装したものが、アクターモデル・ワークキュー（RabbitMQ）・イベントログ（Kafka）である。

## 1. アクターモデルの基本

並行処理のための設計モデル。基本要素は3つ。

- **アクター**: 状態を持つ独立した実行単位。他のアクターと直接メモリを共有しない
- **メールボックス**: 各アクターが持つ、自分宛てのメッセージを溜めておくキュー
- **メッセージ**: アクター間でやり取りする不変（immutable）なデータ

アクターにできることは3つだけ。

1. 他のアクターにメッセージを送る
2. 新しいアクターを作る
3. 次に受け取るメッセージに対する振る舞いを変える（自分の状態を更新する）

**重要な特性**: アクターは自分のメールボックスからメッセージを1件ずつ順番に処理する。だから1つのアクターの内部では「ロックなしで」状態を安全に扱える。並行性の問題（競合状態）は「複数アクター間でどうメッセージを送り合うか」に押し込められる。

代表的な実装: Erlang/Elixir（BEAM VM）、Akka（Scala/Java）、Orleans（.NET）

提唱者はCarl Hewitt（1973年）で、アクターモデル自体は関数型・オブジェクト指向のどちらとも独立した並行計算モデルである。

## 2. Erlang/Elixir OTP でのアクター実装

Elixirではアクターは軽量プロセス（BEAM上のグリーンスレッド）。実務では`GenServer`（Generic Server）という定型パターンを使う。

```elixir
defmodule Counter do
  use GenServer

  # --- クライアントAPI ---
  def start_link(initial \\ 0) do
    GenServer.start_link(__MODULE__, initial, name: __MODULE__)
  end

  def increment(amount \\ 1) do
    GenServer.cast(__MODULE__, {:increment, amount})
  end

  def get_value do
    GenServer.call(__MODULE__, :get_value)
  end

  # --- サーバーコールバック ---
  @impl true
  def init(initial) do
    {:ok, initial}  # これがアクターの「状態」
  end

  @impl true
  def handle_cast({:increment, amount}, state) do
    {:noreply, state + amount}
  end

  @impl true
  def handle_call(:get_value, _from, state) do
    {:reply, state, state}
  end
end
```

- `cast` = 送りっぱなし（非同期、返信を待たない）。アクターモデルの「メッセージ送信」そのもの
- `call` = 送って返信を待つ（内部的にはcast + 受信メッセージを待機。同期っぽく見えるが実装は非同期メッセージのやり取り）
- `state`はプロセス内に閉じていて、`handle_cast`/`handle_call`は1件ずつ順番にしか呼ばれない → ロック不要

実務では`Supervisor`でこのプロセスを監視し、クラッシュしたら自動再起動する（"let it crash"哲学）。これがOTPの核心。

## 3. Akka でのアクター実装（Scala）

### 3.1. Classic Akka Actor（OOP寄り）

```scala
class Counter extends Actor {
  var state = 0  // ミュータブルなフィールド

  def receive = {
    case Increment(n) => state += n        // 破壊的代入
    case GetValue     => sender() ! state
  }
}
```

`class extends Actor`、`var state`で状態をミュータブルに保持する、オブジェクト指向的な設計。

### 3.2. Akka Typed（現行、FP寄り）

```scala
import akka.actor.typed.{ActorSystem, Behavior}
import akka.actor.typed.scaladsl.Behaviors

object Counter {
  sealed trait Command
  final case class Increment(amount: Int) extends Command
  final case class GetValue(replyTo: akka.actor.typed.ActorRef[Int]) extends Command

  def apply(): Behavior[Command] = counting(0)

  private def counting(state: Int): Behavior[Command] =
    Behaviors.receiveMessage {
      case Increment(amount) =>
        counting(state + amount)          // 新しい状態で「なり替わる」= become

      case GetValue(replyTo) =>
        replyTo ! state
        Behaviors.same
    }
}
```

FPの特徴が色濃く出ている点:

- 状態はミュータブル変数ではなく関数の引数（`state: Int`）
- 状態遷移は「今の関数を書き換える」のではなく「新しい関数（Behavior）を値として返す」— 再帰関数の累積引数パターンそのもの
- メッセージは`sealed trait` + `case class`で代数的データ型として表現し、`match`で網羅的にパターンマッチ
- 副作用（`replyTo ! state`）以外はほぼ純粋関数

新APIがFP寄りに設計された理由は実務上のバグ対策。旧APIの`var state`は、非同期メッセージ処理の途中でクロージャや別スレッドから誤って参照・書き換えられるバグを生みやすかった。状態を「関数の引数として明示的に受け渡す」設計にすることで、コンパイラに状態の流れを追わせやすくし、うっかりミュータブル共有するミスを防いでいる。

まとめ:

| | 状態の持ち方 | パラダイム色 |
|---|---|---|
| Classic Akka Actor | `var`フィールド | OOP的 |
| Akka Typed（Behaviors） | 関数の引数として渡す不変値 | FP的 |
| Erlang/Elixir GenServer | 同上（`state`を毎回引数で受け取る） | 生粋のFP言語なので必然的にFP的 |

「Akkaは関数型」というより、「Akkaは元々OOP的に作られたが、現行のTyped APIは関数型プログラミングの手法（不変性・値としての振る舞い・パターンマッチ）を取り入れて設計し直された」というのが正確な理解。Scala自体がマルチパラダイム言語なので、この移行がしやすかったとも言える。

## 4. メッセージキュー（RabbitMQ / Kafka）

アクターのメールボックスとは別レイヤーで、システム間・プロセス間の非同期通信を担うミドルウェア。

### 4.1. RabbitMQ（キュー型）

Producer → exchange（振り分けルール） → queue（バッファ） → Consumer。**処理済みメッセージはキューから消える**。「タスクを1回だけ誰かに処理してほしい」用途向き（ワークキュー）。

```python
# producer.py
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()
channel.queue_declare(queue='task_queue', durable=True)

channel.basic_publish(
    exchange='',
    routing_key='task_queue',
    body='hello',
    properties=pika.BasicProperties(delivery_mode=2)  # メッセージ永続化
)
connection.close()
```

```python
# consumer.py
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()
channel.queue_declare(queue='task_queue', durable=True)
channel.basic_qos(prefetch_count=1)  # 1件処理し終わるまで次を配らない

def callback(ch, method, properties, body):
    print(f"received {body}")
    ch.basic_ack(delivery_tag=method.delivery_tag)  # 処理完了を明示的にack

channel.basic_consume(queue='task_queue', on_message_callback=callback)
channel.start_consuming()
```

#### 4.1.1. Exchangeの種類

ProducerはQueueに直接送らず、必ずExchangeを経由する。Exchangeの種類によってルーティングの振る舞いが変わる。

| 種類 | 説明 |
|---|---|
| Direct | ルーティングキーが完全一致するQueueに送る |
| Fanout | バインドされた全Queueにブロードキャスト |
| Topic | `*`（1語）・`#`（0語以上）のワイルドカードでパターンマッチ |
| Headers | ルーティングキーでなくヘッダー属性でマッチング |

#### 4.1.2. 信頼性まわりの機能

- **Ack/Nack**: Consumerが処理完了を明示的に通知（`basic_ack`）。処理に失敗したら`basic_nack`で再配信させられる
- **Dead Letter Exchange (DLX)**: 一定回数リトライしても処理できないメッセージを別Exchangeに転送し、隔離・別処理する仕組み
- **durable / delivery_mode=2**: Queueとメッセージ双方をこの設定にすることで、ブローカー再起動後もデータが残る
- **クラスタリング/ミラーリング**: 複数ノード構成での高可用性
- **管理UI**: 管理プラグイン（ポート15672）でブラウザからQueue状況やメッセージレートを監視できる

### 4.2. Kafka（ログ型）

メッセージはtopicの中のpartition（追記専用ログ）に保存され、**消費してもすぐには消えない**（保持期間だけ残る）。consumerは自分がどこまで読んだか（offset）を自分で管理する。だから同じデータを複数のconsumer groupがそれぞれ独立に読み直せる（例: 「注文処理」groupと「分析集計」groupが同じ`orders` topicを別々に読む）。

```python
# producer.py
from kafka import KafkaProducer
import json

producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    value_serializer=lambda v: json.dumps(v).encode('utf-8')
)
producer.send('orders', {'order_id': 123, 'amount': 500})
producer.flush()
```

```python
# consumer.py
from kafka import KafkaConsumer
import json

consumer = KafkaConsumer(
    'orders',
    bootstrap_servers='localhost:9092',
    group_id='order-processors',      # 同じgroup_idは負荷分散、別group_idは全員に配信
    value_deserializer=lambda v: json.loads(v.decode('utf-8')),
    auto_offset_reset='earliest'
)
for message in consumer:
    print(f"partition={message.partition} offset={message.offset} value={message.value}")
```

### 4.3. 使い分けの勘所

| | RabbitMQ | Kafka |
|---|---|---|
| モデル | キュー（消費したら消える） | ログ（消費しても残る） |
| 得意 | 複雑なルーティング、タスク分配、優先度 | 高スループット、イベントの再生・複数消費者への配信 |
| スループット | 数万msg/s級 | 数十万〜百万msg/s級 |
| 典型用途 | ジョブキュー、RPC | イベントソーシング、ログ集約、ストリーム処理 |

## 5. 3レイヤーの全体像

```
[プロセス内]         Elixirプロセス / Akkaアクター  ← メールボックス（揮発性、1プロセス専用）
[マシン内複数プロセス] RabbitMQ                      ← キュー（永続化、タスク分配）
[サービス間・大規模]   Kafka                         ← ログ（永続化、イベント配信・再生）
```

アクターモデルは「1台のマシン内のマルチスレッド問題を解く」ための道具、メッセージキューは「複数のサービス・マシンをまたいで疎結合にする」ための道具、という整理ができる。ただし概念自体は似ており、Akkaのような分散アクターシステムでは、アクターがネットワークをまたいで配置され、メッセージキュー的な役割（永続化・再送）を担うこともある（Akka Persistence, Akka Clusterなど）。
