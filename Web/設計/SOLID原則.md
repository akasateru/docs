# SOLID原則

オブジェクト指向設計（[プログラミングパラダイム](../Programing/プログラミングパラダイム.md)参照）の4本柱を、実務でどう適用すれば壊れにくい設計になるかを示す5つの指針。

## 1. S: Single Responsibility Principle（単一責任の原則）

- 1つのクラスは1つの責任（＝変更する理由）だけを持つべき。
- 変更する理由が2つ以上あるクラスは、1つの変更が他の機能に予期せぬ影響を及ぼすリスクを持つ。
- 例: `UserManager`が「ユーザー情報の保存」と「メール送信」を両方担うと、メール仕様変更のたびにユーザー保存ロジックまで触るクラスを再デプロイするリスクが生まれる。分離すべき。

## 2. O: Open/Closed Principle（オープン・クローズドの原則）

- 拡張に対しては開いていて、修正に対しては閉じているべき。
- 新機能を追加する際、既存コードを書き換えず新しいクラスを追加するだけで対応できる設計を目指す。
- 実現手段: 抽象化（インターフェース）＋ポリモーフィズム。例: `shape.draw()`という抽象に対し新しい図形クラス`Triangle`を追加しても、呼び出し側の既存コードは変更不要。

## 3. L: Liskov Substitution Principle（リスコフの置換原則）

- サブクラスは親クラスと置き換えても正しく動作しなければならない。
- 継承の「is-a関係が成立していないと壊れる」という制約を明文化したもの。
- 有名な反例: 「正方形は長方形の一種」として`Square`を`Rectangle`から継承すると、`Rectangle`の「幅と高さを独立に変更できる」という前提が`Square`では成り立たず、置き換えると壊れる。数学的な「is-a」とプログラム上の「振る舞いの互換性」は別物。

## 4. I: Interface Segregation Principle（インターフェース分離の原則）

- クライアントが使わないメソッドへの依存を強制すべきではない。
- 巨大な1つのインターフェースより、用途ごとに小さく分けたインターフェースを複数用意する方がよい。
- 例: `Printer`に`print()`/`scan()`/`fax()`を全部詰め込むと、印刷しかしないデバイスも使わない`scan()`の実装を強制される。`Printable`/`Scannable`/`Faxable`に分けるべき。

## 5. D: Dependency Inversion Principle（依存性逆転の原則）

- 上位モジュールは下位モジュールに依存すべきではなく、両方とも抽象に依存すべき。
- 上位（ビジネスロジック）が下位（DB接続やAPIクライアントなどの具体的な実装）に直接依存すると、下位の変更が上位に波及する。間に抽象（インターフェース）を挟み、両方がその抽象に依存する形にすることで、下位の実装を差し替え可能にする。
- DI（Dependency Injection）コンテナの理論的な裏付けになっている原則。

## 6. 全体の繋がり

- S: クラスの粒度の指針。
- O・L: 継承・ポリモーフィズムを安全に使うための指針。
- I・D: 抽象化をどう設計すべきかの指針。
- OOPの4本柱（抽象化・継承・ポリモーフィズム・カプセル化）に対して、SOLIDは「それを具体的にどう適用すれば壊れにくいか」の運用ルールという関係にある。

## 7. 覚え方（たとえ話）

学級の「係活動」に例えると直感的に理解しやすい。

| 原則 | たとえ |
| --- | --- |
| S | 給食係は給食だけ、黒板係は黒板だけ（一人一役） |
| O | 新しい係（本係）は追加できるが、既存の係（給食係）のルールは変えない |
| L | 係を交代しても、同じルールで同じように仕事が回る |
| I | 図書係に掃除や窓ふきまで押し付けない（必要な仕事だけ任せる） |
| D | 「◯◯くん」ではなく「給食係」という役割に頼む（具体的な人ではなく役割に依存する） |
