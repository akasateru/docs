# 1. 依存性の注入（Dependency Injection）

**依存性の注入 = 「必要なものを自分で作らず、外から渡してもらう」設計手法。**

## 1.1. 用語

- **依存（dependency）**: あるクラスが動作するために必要とする「他のオブジェクト」。例えば `注文処理` クラスが `メール送信` 機能を使うなら、`注文処理` は `メール送信` に依存している。
- **注入（injection）**: 依存するオブジェクトを、自分自身で作る（`new`する）のではなく、外部から渡してもらうこと。

## 1.2. Before/After の例

DIを使わない場合（依存を自分で作ってしまう）:

```java
class 注文処理 {
    private メール送信 mailer = new メール送信(); // 自分で作ってしまう

    void 注文完了(注文 order) {
        mailer.送る(order.email, "注文完了しました");
    }
}
```

DIを使った場合（コンストラクタで外から渡してもらう）:

```java
class 注文処理 {
    private メール送信 mailer;

    注文処理(メール送信 mailer) { // コンストラクタ注入
        this.mailer = mailer;
    }

    void 注文完了(注文 order) {
        mailer.送る(order.email, "注文完了しました");
    }
}

// 使う側
メール送信 mailer = new メール送信();
注文処理 processor = new 注文処理(mailer); // 外から渡す = 注入
```

変わったのは「`new メール送信()` する場所を `注文処理` クラスの中から外に移した」ことだけ。それ以外の処理は同じ。

## 1.3. 得られるメリット

| メリット | 説明 |
| --- | --- |
| テストしやすくなる | テスト時は本物の依存の代わりに「偽物（テストダブル）」を注入できる。`注文処理` 側のコードは変えずに済む |
| 差し替えが楽になる | メール送信をSMS送信に変えても、同じインターフェースを実装していれば `注文処理` の中身は無変更で済む |
| 結合度が下がる | クラスは「メールを送れる何か」がある、という抽象的な知識だけを持ち、具体的な実装を知らなくて済む |

## 1.4. 人に教えるときのコツ（2026-08-02時点のログ）

- 一言でまとめると刺さりやすい: 「`new`する場所を、使う側から呼び出し元に引っ越しさせるだけ」。
- 説明の順序が重要。DIコンテナ（Spring、Guiceなど）の話から入ると本質が埋もれるため、以下の順で進める。
  1. 手動でのコンストラクタ注入（コード例で体験させる）
  2. なぜ嬉しいか（テスト容易性・差し替え・結合度）
  3. 最後にDIコンテナは「注入を自動化する省力化ツール」に過ぎないと補足する
- DIコンテナはDIの本質ではない。コンテナなしでも上記のコード例だけでDIは成立する。

## 2. ワイヤリング（配線）

**ワイヤリング = 「どのインターフェース（抽象）に対して、どの実装（具象）を結びつけるか」を決定・登録する作業。**

DIそのものは「外から渡してもらう」という設計原則だが、実際に渡す側（呼び出し元・エントリポイント・コンテナ）で「具体的に何を渡すか」を決めて配線する必要がある。この配線作業がワイヤリング。

### 2.1. ワイヤリングの2方式

| 方式 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| 手動ワイヤリング（Pure DI） | エントリポイントなどで依存関係を手で `new` して組み立てる | 追加ライブラリ不要、依存関係がコードとして追いやすい | 依存グラフが大きくなると組み立てコードが煩雑になる |
| DIコンテナによる自動ワイヤリング | フレームワーク（Spring、dependency-injector、NestJSなど）が型やアノテーションを見て自動的に依存を解決・注入する | 大規模になっても配線コードが増えにくい | コンテナの挙動を理解しないと「どこで何が注入されているか」が追いにくい |

手動ワイヤリングの例（Python）:

```python
def main():
    repo = PostgresOrderRepository(db_conn)
    notifier = EmailNotifier(smtp_client)
    service = OrderService(repo, notifier)
    service.run()
```

DIコンテナによる自動ワイヤリングの例（TypeScript / NestJS）:

```typescript
@Module({
  providers: [
    { provide: OrderRepository, useClass: PostgresOrderRepository },
    OrderService,
  ],
})
class OrderModule {}
```

### 2.2. ワイヤリングで決めること

- **バインディング**: どのインターフェースにどの実装を対応させるか（例: 本番はPostgres実装、テストはInMemory実装）
- **スコープ/ライフサイクル**: Singleton（アプリ全体で1インスタンス）/ Transient（呼ぶたびに新規生成）/ Scoped（リクエスト単位など）のいずれで管理するか
- **注入方法**: コンストラクタ注入（推奨）/ セッター注入 / フィールド注入のどれを使うか
- **環境ごとの切り替え**: 本番・テスト・ローカルで異なる実装を注入する（テスト容易性向上の主目的の一つ）
