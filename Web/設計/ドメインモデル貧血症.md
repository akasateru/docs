## 1. ドメインモデル貧血症（Anemic Domain Model）

- Martin Fowlerが指摘したアンチパターン。ドメインのクラスが**データ（getter/setterに近い属性）だけ**を持ち、業務ロジックが外部の「サービス層」に集中している状態。
- オブジェクト指向の本質である「データと振る舞いを1つの箱にまとめる」ことができておらず、`class`という構文だけがオブジェクト指向で、実質的な中身は手続き型と変わらない。

### 1.1. 典型的な症状

```python
# 貧血気味なドメインモデル：データだけの入れ物
class Order:
    def __init__(self, items, status):
        self.items = items
        self.status = status

# ロジックは全部「サービス層」という手続き的な場所に集まる
class OrderService:
    def cancel(self, order: Order):
        if order.status == "shipped":
            raise Exception("発送済みはキャンセルできません")
        order.status = "cancelled"

    def calculate_total(self, order: Order):
        return sum(item.price for item in order.items)
```

対して「リッチなドメインモデル（Rich Domain Model）」は、データと自身に関するルールを1つのクラスに戻す。

```python
class Order:
    def __init__(self, items, status):
        self.items = items
        self.status = status

    def cancel(self):
        if self.status == "shipped":
            raise Exception("発送済みはキャンセルできません")
        self.status = "cancelled"

    def total(self):
        return sum(item.price for item in self.items)
```

### 1.2. 何が問題になるか

- 同じビジネスルールが`OrderService`、`UserService`などの複数のサービスクラスに重複しやすい。
- ドメインクラス自体を見ても「そのドメインが何をできるか」がわからず、仕様を把握するにはサービス層を全部読む必要がある。
- クラスは存在するのに、オブジェクト指向のメリット（カプセル化・凝集度の高さ）を享受できていない。

### 1.3. 既存プロジェクトで見つけた場合の判断基準

ある程度進んだプロジェクトで貧血ドメインモデルが既に定着している場合の判断。

- **基本方針は「今の慣習に従う」**。一部のドメインだけリッチ化すると設計スタイルが混在し、かえって読みにくくなり、チーム全体の学習コストも上がる。一貫性の価値は個々のクラス設計の美しさより大きいことが多い。
- **例外的にリファクタリングを検討してよいケース**。
  - 同じビジネスルールが複数箇所に重複していて、実際にバグの温床になっている。
  - そのドメインを頻繁に触っていて、現状の構造で実務上困っている。
- 「なんとなく設計として綺麗じゃない」という理由だけで全体を書き直すのは、リスクに見合わないことが多い。困っている箇所だけを限定的に、振る舞いをモデルに寄せる小さなリファクタリングをするのが現実的。

## 2. ActiveRecordモデルとは

- Martin Fowlerが著書『Patterns of Enterprise Application Architecture』で定義したアーキテクチャパターンの1つ。**DBテーブルの1行を1オブジェクトにラップし、そのオブジェクト自身にCRUD（`save`・`find`・`delete`など）の永続化ロジックを持たせる**設計。
- Railsの`ActiveRecord::Base`や、Djangoの`models.Model`などが代表的な実装。
- ドメインモデルパターンとの違い。
  - ドメインモデル：業務ロジックを持つオブジェクトと、永続化（DBアクセス）を担うRepository/DAOを分離する。
  - ActiveRecord：オブジェクトの構造がテーブルの列構造とほぼ1:1に対応し、永続化ロジックと（あれば）業務ロジックが同じクラスに同居する。

### 2.1. なぜ貧血症になりやすいか

- ActiveRecordはテーブル構造ありきの設計になりやすく、複雑な業務ロジックを持たせるとクラスが肥大化・責務過多になる。
- それを避けるため、業務ロジックを別の「サービス層」に逃がす実装が広まりやすく、結果としてActiveRecordクラス自体はgetter/setterとDBアクセスだけを持つ貧血な入れ物になりがち。
- ただしこれはActiveRecordパターン自体の欠陥というより、**永続化とドメインロジックを同じクラスに同居させる設計上、業務ロジックの置き場に迷った結果として貧血化しやすい**という傾向の話。ActiveRecordを使いつつ、モデル自身に業務ロジック（`cancel()`や`total()`など）を持たせてリッチにすることは可能。
