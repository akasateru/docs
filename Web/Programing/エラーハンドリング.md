# 1. エラーハンドリングのベストプラクティス

言語・フレームワークを問わず適用できる、エラー処理の設計原則。

## 1.1. 例外は異常系にのみ使う

- 正常系のフロー制御に例外を用いない。バリデーションエラーなど予測可能なケースは戻り値や `Result`/`Optional` 型で表現する方が読みやすい。
- Go はエラーを戻り値として返す文化、Python/TypeScript は `Result` 型ライブラリで代替可能。

## 1.2. 握りつぶさない（silent failure の禁止）

- `except Exception: pass` のような空catchは最も避けるべきパターン。原因不明のバグを埋め込む温床になる。
- 最低限ログを残す、または再raiseして上位に伝播させる。

```python
try:
    do_something()
except SpecificError as e:
    logger.error(f"do_something failed: {e}")
    raise
```

## 1.3. 例外は具体的な型で捕捉する

- `catch (Exception)` / `except Exception` のような広すぎる捕捉は、意図しない例外（NullPointerなど）まで隠してしまう。
- 想定している例外だけをキャッチし、想定外は上位に伝播させる。

## 1.4. エラーメッセージにコンテキストを持たせる

- 「何が」「なぜ」失敗したかを含める。スタックトレースだけでは原因調査に時間がかかる。

```python
raise ValueError(f"Invalid user_id={user_id}: must be positive integer")
```

## 1.5. 失敗の境界（バウンダリ）を決めてラップする

- 外部API呼び出し・DB操作・ファイルI/Oなど「失敗しうる場所」を明確にし、そこで意味のあるドメインエラーに変換する。
- Python の `raise ... from e` のように、元の例外チェーンを保持する。

```python
try:
    response = requests.get(url, timeout=5)
except requests.RequestException as e:
    raise ExternalServiceError(f"Failed to fetch {url}") from e
```

## 1.6. リトライは冪等性を確認してから

- ネットワークエラーなど一時的な失敗は指数バックオフでリトライする。
- 副作用のある処理（決済、書き込み）は冪等性キーなどで重複実行を防ぐ。

## 1.7. リソース解放を保証する

- try/finally や `with`（コンテキストマネージャ）でクリーンアップを保証し、手動close()忘れを防ぐ。

```python
with open(path) as f:
    process(f)
```

## 1.8. ユーザー向けメッセージと内部ログを分離する

- ユーザーには「決済に失敗しました。時間をおいて再試行してください」のような平易な文言を返す。
- 内部ログには詳細なスタックトレース・入力値・リクエストIDを残す。
- パスワード・トークンなどセンシティブ情報はログに出さない。

## 1.9. Fail Fast（早期に落とす）

- 不正な状態を早い段階で検出し、深いところまで伝播させない（前提条件チェック、アサーション）。

## 1.10. 監視・アラートと連携する

- 例外を握るだけでなく、Sentryなどのエラートラッキングツールに送る。
- 重大度に応じてアラートを発火する。
