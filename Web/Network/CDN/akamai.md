## 1. Akamai

## 2. Akamaiの主要サービス

### 2.1. Content Delivery (CDN)

最も有名な機能。画像、動画、HTML などをユーザーのすぐ近くのサーバーにキャッシュし、高速配信する。

- **Google Cloud との比較:** Google Cloud の CDN よりも拠点が圧倒的に多く、世界のどこからでも低レイテンシで配信できるのが強み。

### 2.2. Edge DNS

世界中に分散された権威 DNS サービス。

- **特徴:** 100% の稼働率（SLA）を保証しており、大規模な DDoS 攻撃を受けても DNS 応答が止まりません。ドメイン解決（名前解決）の段階で、最も近い Edge サーバーへ誘導する役割も担っています。

### 2.3. EdgeWorkers (エッジコンピューティング)

Cloud Run よりもさらにユーザーに近い場所で、**JavaScript コードを実行**できる FaaS（Function as a Service）です。

- **活用例:**

  - ユーザーの国やデバイスに応じて HTTP ヘッダーを書き換える。
  - A/B テストの振り分けをエッジで行い、オリジン（Cloud Run 等）の負荷を減らす。
  - セキュリティチェックをエッジで完結させる。

## 3. エンジニアが Akamai を導入する主な理由

自社プロダクトを Cloud Run や GCE で動かしている場合でも、その「手前」に Akamai を置く構成はよくあります。

| 目的               | 内容                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| **DDoS 対策**      | 攻撃がクラウド（GCP）に届く前の「エッジ」で遮断するため、バックエンドがパンクしない                          |
| **グローバル対応** | 海外ユーザーが多い場合、東京リージョンの Cloud Run だけでは遅いため、Akamai で世界中にキャッシュをばら撒く。 |
| **負荷分散**       | 複雑なルーティング（特定のパスだけ別のサーバーに飛ばす等）を、エッジ側で柔軟に制御できる。                   |

## 4. Bot Manager

不正なボットトラフィック（スクレイピング、クレデンシャルスタッフィング等）を検知・制御するセキュリティ製品。

### 4.1. IP レピュテーション

**IP レピュテーション**とは、特定の IP アドレスの「過去の素行」をスコアリングし、そのアクセスが悪意あるものかを判定する仕組み（IP 版の信用スコア）。

- **評価元データ:** Akamai は世界のインターネットトラフィックのかなりの割合を経由しているため、その規模を活かしたグローバルな脅威インテリジェンスで各 IP を継続的に評価している。
- **評価に使われる要素の例:**
  - 過去に DDoS 攻撃・スクレイピング・クレデンシャルスタッフィングに使われた実績があるか
  - データセンター/ホスティングプロバイダの IP か（一般ユーザーが使うことは少なく、ボットの可能性が高い）
  - VPN・プロキシ・Tor の出口ノードか
  - 既知のボットネットに属しているか
  - リクエストパターンの異常性（急激なアクセス増加、複数サイトへの同時アクセス等）
- これらを元に IP ごとにリスクスコアやカテゴリ（例: `Suspicious`、`Malicious`、`Good bot` 等）を付与する。

### 4.2. 他シグナルとの組み合わせ

IP レピュテーションは**単独では使わず**、以下のような他のシグナルと組み合わせて最終判定する。単独判定だと誤検知（false positive）が多くなるため。

| シグナル                       | 説明                                       |
| ------------------------------ | ------------------------------------------ |
| IP レピュテーション            | その IP の過去の素行                       |
| デバイスフィンガープリンティング | ブラウザ/デバイスの特徴                    |
| 振る舞い分析                   | マウスの動き、クリックパターンなど人間らしさ |
| リクエストヘッダー異常検知     | User-Agent の矛盾など                      |

誤検知が起きやすい代表例:

- 企業のプロキシや NAT の裏に大量の正規ユーザーがいる場合、同一 IP からの大量アクセスに見える
- モバイルキャリアの IP は多数のユーザーで共有されている
- 悪評 IP でもその後正常化している場合がある（逆も然り）

これらのシグナルをリスクスコアとして合算し、最終的に「許可 / チャレンジ（CAPTCHA 等）/ モニタリングのみ / ブロック」といったアクションを決定するのが一般的な運用。

### 4.3. 実務上のポイント

- 管理コンソールでは、IP レピュテーションによる検知結果をカテゴリ別（例: `Web Attackers`、`Denial of Service` 等）に確認できる。
- 誤検知防止のため、自社の正規トラフィック（社内 VPN 経由のテストアクセス等）が悪評 IP レンジに該当していないか確認することが重要。
- ルール設定では、IP レピュテーションのしきい値だけで即ブロックせず、他のボット検知シグナルとの複合条件でアクションを設定することが推奨される。
