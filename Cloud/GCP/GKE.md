GKE(Google Kubernetes Engine)はGoogle CloudのマネージドKubernetesサービス。クラスタはコントロールプレーンとworker nodeで構成される。

## 1. クラスタの構成要素

### 1.1. コントロールプレーン(Control Plane)

- Kubernetes APIサーバー、スケジューラ、etcdなどを管理する頭脳部分
- GKEでは基本的にGoogle側がフルマネージドで運用し、ユーザーからは直接見えない

### 1.2. worker node

- 実際にアプリケーションのPodがスケジュールされ、動く場所
- GCEのVMインスタンスとして起動する
- 各worker nodeで動いているもの
  - **kubelet**: コントロールプレーンと通信し、Podの起動・監視を担当するエージェント
  - **kube-proxy**: Service宛の通信をPodにルーティングするネットワークプロキシ
  - **container runtime**(containerdなど): 実際にコンテナを起動・実行する
  - 実行中の**Pod群**

## 2. Node Pool

- 同じ設定(マシンタイプ、ディスク、ラベルなど)を持つworker nodeの集合
- 用途別(例: CPU用/GPU用)に複数のNode Poolを作れる

## 3. Autopilot vs Standard

|  | Standard | Autopilot |
|---|---|---|
| ノード管理 | ユーザーが管理 | Googleが完全管理(ノードレス) |
| 課金単位 | ノード(VM)単位 | Pod単位(実際に使ったCPU/メモリ) |
| ノードへのSSHアクセス | 可能 | 不可 |
| セキュリティ設定 | 自分で設定 | ベストプラクティスが強制適用 |
| DaemonSetの自前作成 | 可能 | 制限あり([5.](#5-daemonset)参照) |

### 3.1. Autopilotの特徴

- **ノードレス運用**: ノードのプロビジョニング・スケーリング・アップグレード・修復をGoogleが自動化。ノードプールの設計やサイジングを考える必要がない
- **Pod単位の課金**: Podが実際にリクエストしたCPU/メモリ/ストレージに対して課金されるため、Standardのような「ノードの空きリソースの無駄」が起きにくい。ただしリソースリクエストの過不足がそのままコストに直結する
- **セキュリティの強制**: 特権コンテナ(privileged)やホスト共有機能の一部が使えない。Workload Identityがデフォルト有効、Shielded GKE Nodesなども自動適用される

### 3.2. Autopilotのメリット・デメリット

- メリット: 運用負荷の削減(ノード管理・パッチ適用・キャパシティプランニング不要)、過剰プロビジョニングが起きにくくコスト最適化されやすい、SLAがPod単位で提供される
- デメリット: DaemonSetなど一部のワークロードタイプに制限がある、特権コンテナやホストネットワークが必要な特殊ワークロードが動かせないことがある、ノードレベルの細かいチューニング(カスタムカーネルパラメータ等)ができない

### 3.3. 使い分けの目安

- Autopilot向き: Kubernetes運用に時間を割きたくない、標準的なステートレス/ステートフルワークロードが中心、セキュリティのベストプラクティスを最初から強制したい
- Standard向き: 自前のノードエージェント(DaemonSet)が必要、特権コンテナやホストレベルのアクセスが必要なワークロードがある

## 4. Autoscaling

- 負荷に応じてNode Poolのノード数を自動増減できる(Cluster Autoscaler)
- ノードが故障・削除されると、その上のPodは別のノードに再スケジュールされる(Kubernetesの自己修復性の一部)

## 5. DaemonSet

クラスタ内の(条件に合う)すべてのノードに、Podを1つずつ必ず配置するワークロードリソース。

### 5.1. Deploymentとの違い

|  | Deployment | DaemonSet |
|---|---|---|
| Pod数の決め方 | replicas数で指定 | ノード数に応じて自動的に決まる |
| スケジューリング | 空いているノードにスケジューラが配置 | 全ノード(対象ノード)に1つずつ強制配置 |
| ノード追加時 | 何もしない | 新ノードにも自動でPodが追加される |
| ノード削除時 | 何もしない | そのノード上のPodも一緒に消える |

### 5.2. 典型的な用途

ノードごとに1つ動いていてほしい「インフラ的な」プロセスに使われる。

- **ログ収集エージェント**(Fluentd、Fluent Bitなど): 各ノードのログを集めてどこかに転送
- **監視・メトリクス収集**(Node Exporter、Datadog Agentなど): ノードのCPU/メモリ等を計測
- **ネットワークプラグイン**(CNIのコンポーネント、kube-proxyなど): 各ノードのネットワーク設定
- **セキュリティエージェント**(Falcoなど): ノード上での不審な挙動の検知
- **ストレージデーモン**(Cephのノードエージェントなど)

`nodeSelector`や`tolerations`で「特定ラベルが付いたノードだけ」に絞ることもできる(例: GPUノードだけにドライバ管理エージェントを配置)。

### 5.3. Autopilotとの関係

Autopilotではユーザー自身のDaemonSet作成が制限されている。Autopilotはノードをユーザーから隠蔽・完全管理するモデルであり、「全ノードに強制的にPodを置く」という前提がノード管理の抽象化と衝突するため。

- ログ収集や監視などDaemonSetが担っていた役割は、Google管理のシステムコンポーネントとして裏側で自動的に提供される(Cloud Logging/Cloud Monitoringへの連携が標準で組み込み済み)
- 自前のノードエージェントがどうしても必要な場合はAutopilotではなくStandardモードを選ぶ必要がある
