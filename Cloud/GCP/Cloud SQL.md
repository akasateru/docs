# Cloud SQL

Google Cloudのフルマネージド型RDBMS（MySQL/PostgreSQL/SQL Server互換）。分散DB全般の理論的背景（レプリケーション・シャーディング・CAP定理・合意形成など）は[Database](../../Web/Database/Database.md)を参照。

## 1. Read Pool（読み取りプール）

複数の読み取りレプリカを**1つの読み取りエンドポイント**の裏にまとめ、大量の読み取り負荷をプライマリから逃がすための機能。MySQL・PostgreSQL両方で提供され、Cloud SQL Enterprise Plusエディションで一般提供（GA）。

- **オートスケーリング**: CPU使用率またはDB接続数をメトリクスとして、ノード数を**1〜20の範囲**で自動増減。両方のメトリクスを有効にした場合は、それぞれが示すノード数のうち大きい方が採用される
- **垂直スケーリング**: 全ノード一律でマシンタイプの変更も可能
- アプリ側は単一の読み取りエンドポイントを見るだけでよく、レプリカの追加・削除に伴う接続設定変更が不要

## 2. Read Poolと高可用性（HA）の違い

名前が紛らわしいが、目的も仕組みも別機能。

| | Read Pool | 高可用性（HA） |
| --- | --- | --- |
| 目的 | 読み取り負荷分散（スケーリング） | 障害時の可用性確保 |
| 複製方式 | 非同期 | 同期（別ゾーンにスタンバイ） |
| 読み取り用途 | 可（そのためにある） | 不可（スタンバイは読み取り非公開） |
| 障害時の昇格 | **不可**（公式ドキュメントで「レプリカの昇格はサポート対象外」と明記） | 自動フェイルオーバーで昇格 |

Read Poolのノードは「プライマリから直接レプリケーションを受ける」構成が必須で、独立した障害復旧先として機能する設計にはなっていない。**障害時に自動で継投してほしいなら、Read Poolとは別にHAを有効化する必要がある。**

## 3. 通常の（プールではない）手動リードレプリカ

Read Poolを使わず、個別に作成した読み取りレプリカは、それぞれ名前とインスタンスIDを持つ独立したインスタンスとして扱われる。この場合は

```bash
gcloud sql instances promote-replica REPLICA_INSTANCE_NAME
```

で個別に選んでプライマリへ昇格させることができる。ただし非同期複製である点は変わらないため、昇格時にレプリケーション遅延分のデータロスが起きうる（[Database §17 RPOとRTO](../../Web/Database/Database.md)参照）のと、HAのように自動では実行されず手動操作である点に注意。

## 4. まとめ: 目的ごとの機能の使い分け

- **読み取りをスケールさせたい** → Read Pool
- **リージョン内障害に自動対応したい** → HA
- **個別にDR用の予備を持ちたい** → 手動リードレプリカ（§3）を作成し、必要に応じて手動昇格
