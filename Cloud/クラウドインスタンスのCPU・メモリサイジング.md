# 1. クラウドインスタンスのCPU・メモリサイジング

クラウド(AWS/GCP等)のインスタンスにおける「vCPU」「メモリ(GB)」の意味と、スペックから性能を見積もる際の体感・目安をまとめる。

## 1.1. vCPU(仮想CPU)とは

- **vCPU = virtual CPU**。物理CPUのコア(またはハイパースレッド)を仮想化して、インスタンスに割り当てた論理的な処理単位。
- 「8vCPU」なら、そのインスタンスは8スレッド分の処理を並列に実行できるという意味。
- 物理コア数とは厳密には一致しない。ハイパースレッディング有効時は「1物理コア = 2vCPU」の対応が多く、8vCPUは物理コア4〜8個程度に相当することが多い(クラウド事業者・インスタンスタイプによる)。

## 1.2. CPUバウンドとI/Oバウンド

処理のボトルネックがどこにあるかで、vCPU数の効き方が変わる。

- **CPUバウンドな処理**: 処理時間のボトルネックがCPUの計算速度そのものにある処理。CPUを使い切るまで計算し続け、待ち時間がほとんどない。例: 画像リサイズ、暗号化/ハッシュ計算、数値計算、トークナイズ、正規表現の大量マッチング。`top`/`htop`でCPU使用率がずっと100%に張り付く。
- **I/Oバウンドな処理**: 処理時間の大半がディスク/ネットワーク/DBの応答待ちで、CPU自体はほとんど仕事をしていない。例: Webサーバーがクライアントのリクエストを受けてDBの返事を待っている時間。CPU使用率は低いのに処理が遅く見える。

CPUバウンドな処理は「CPUを増やせば比例して速くなりやすい」が、I/Oバウンドな処理は「CPUを増やしてもあまり速くならない(待ち時間自体は減らない)」という違いが出る。

| vCPU数 | CPUバウンド処理の体感 | I/Oバウンド(Webサーバー等)の体感 |
|---|---|---|
| 2 | マルチプロセスで2並列まで実質フルスピード | 小規模API、同時数十リクエスト |
| 4 | 並列化で2〜4倍速 | 中規模API、同時100リクエスト程度 |
| 8 | マルチプロセスで8並列、重いバッチが実用速度に | 余裕のあるAPIサーバー |
| 16〜32 | 分散処理ワーカー1台分、本格的な並列バッチ | 大規模トラフィックを1台で捌けるレベル |

## 1.3. メモリ(GB)とは

- 搭載RAM容量。「32GB」ならそのマシン上で動くプロセス全体が使えるメモリの上限が32GB。
- 不足するとスワップが発生して極端に遅くなったり、OOM Killerでプロセスが強制終了されたりする。
- データ処理系(pandas等)では「元データのファイルサイズの3〜5倍のメモリ」が目安(Pythonオブジェクトの管理情報や処理中の一時コピーなど、本来のデータサイズ以外にかかる余分なメモリ消費=**オーバーヘッド**が発生するため)。データ単位の基礎は [データ単位とファイルサイズの目安](../General/データ単位とファイルサイズの目安.md) を参照。
- 「オーバーヘッド」は遅延(レイテンシ)と同義ではなく、本来の目的の処理以外にかかる余分なコスト全般を指す言葉。文脈によって「余分な処理時間」の場合も「余分なメモリ消費」の場合もある。

## 1.4. なぜCPU数とメモリ量は比例した構成で売られているのか

クラウドの汎用インスタンス(AWSの`m5`系等)でvCPU数とメモリ量がセットで比例しているのには理由がある。

1. **並列処理はそれぞれがメモリを消費する**: 8並列でプロセスを動かすなら各プロセスが自分のぶんのデータをメモリに持つ必要があり、CPUだけ増やしてメモリが足りないと並列化してもすぐメモリ不足になる(スワップで逆に遅くなる)。
2. **ハードウェア構成上の制約**: 物理サーバーのCPUソケットが扱えるメモリチャネル数はコア数に応じて設計されており、クラウド事業者は物理サーバーを論理的に切り分けてインスタンスを提供するため、自然とCPU数とメモリ量が比例した構成になる。

ただし比率はワークロードの性質に応じて選ぶべきもので、クラウド事業者は用途別に比率の異なるインスタンスタイプを用意している。

| インスタンスタイプ例(AWS) | 比率(1vCPUあたり) | 向いている用途 |
|---|---|---|
| 汎用型(`m5`系) | 約4GB | バランス型、一般的なAPI/アプリ |
| コンピュート最適化(`c5`系) | 約2GB | CPUバウンドな計算処理(数値計算、動画エンコード) |
| メモリ最適化(`r5`系) | 約8GB | メモリバウンドな処理(インメモリDB、キャッシュ、大規模データ分析、LLM推論) |

## 1.5. 分散処理ワーカー(Spark等)

Apache Sparkのような分散処理フレームワークでは、大量データを複数マシンに分割して並列処理する。

- **Driver**: 全体の処理計画を立てて指揮する司令塔(1台)。
- **Worker(ワーカー)**: Driverの指示を受けて実際の計算処理を行う実行部隊(複数台)。

「Sparkワーカー1台分のスペック」という言い方は、分散処理クラスタを構成する各ノードのCPU/メモリ構成を指す。例えば16vCPU/64GBのワーカーを複数台並べ、巨大なデータセットを分割しながら各ワーカーが並列で処理する。

## 1.6. LLM推論に必要なメモリの目安

LLMをCPU/メモリ上で動かす場合、重みのロードに必要なメモリは概ね「パラメータ数 × 1パラメータあたりのバイト数」で見積もれる。

| 量子化 | bytes/param | 7Bモデル | 13Bモデル | 70Bモデル |
|---|---|---|---|---|
| FP16 | 2 | 約14GB | 約26GB | 約140GB |
| INT8 | 1 | 約7GB | 約13GB | 約70GB |
| INT4 | 0.5 | 約3.5GB | 約6.5GB | 約35GB |

- これに加えて**KVキャッシュ**分のメモリが必要。TransformerのAttention計算では、各トークン生成時に過去の全トークンに対する計算が必要になるが、毎回計算し直すと無駄が多いため、過去に計算したKey/Valueの値をメモリ上にキャッシュして使い回す仕組みがKVキャッシュ。生成する文章(コンテキスト長)が長くなるほどキャッシュ量が線形に増え、メモリを圧迫する。
- そのため実際に必要なメモリは重みのサイズだけでなく、+20〜30%程度のバッファ(KVキャッシュ+OSのオーバーヘッド)を見ておくと安全。
- ローカルLLMの実行環境としてはGPU/VRAMが前提になることが多い。VRAM容量とモデルサイズの対応は [local LLM](../Web/LLM/local%20LLM.md) を参照。CPU推論(GPUなし)の場合は上記の表がそのままメインメモリの必要量になるが、体感速度はGPU推論よりかなり遅い(数token/秒オーダー)。

## 1.7. 用途別の早見表

| スペック | できること感覚 |
|---|---|
| 2vCPU / 4GB | 個人の検証環境、軽いAPI、小さいデータ(〜1GB)のpandas処理 |
| 4vCPU / 16GB | 中規模API、数GBのデータ処理、7B量子化モデルのCPU推論(遅い) |
| 8vCPU / 32GB | 並列バッチ処理、10GB前後のデータ分析、13B量子化モデルがギリギリ乗る |
| 16vCPU / 64GB | 分散処理ワーカー1台分、30B級の量子化モデル、本番APIの余裕あるサイジング |
| 32vCPU+ / 128GB+ | 大規模データ基盤、70B級の量子化モデルをCPUで(実用速度は別問題) |

上記はあくまで目安であり、実際のワークロードで`htop`/`docker stats`/CloudWatch等でCPU使用率とメモリ使用量を計測し、キャリブレーションするのが最も確実。
